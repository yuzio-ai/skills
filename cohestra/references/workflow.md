# 公共流程 · cohestra v0.3

六阶段为 **need → design → code → review → fix → validate**。quick 是轻量组合入口，不是第七阶段。先读本文件与所选阶段说明，再按需读取任务材料；不默认走完全部阶段。

## 1. 输入、任务与授权

- 从后附 handoff 所在目录或明确任务目录定位 `.cohestra/handoffs/<task-slug>/README.md`，读取有效决定、候选、已有授权与下一步。缺少必要文件时报告缺口，不假设工具之间共享聊天。
- 首次 need/quick 以原始需求为输入，先查看指定任务目录或同目标任务的简短索引；确认没有对应任务后才建目录。使用稳定英文短横线名称，不按工具、会话或执行者重复建任务。其余阶段缺输入时不能另建替代任务。
- 项目入口及 AGENTS 等业务规则继续有效；流程规则和阶段提示词来自本次加载的技能。旧项目中的 prompts/manifest 不作为本次路由或更新来源，也不在普通阶段删改；旧任务中的确认决定与验收要求继续生效。
- 只读阶段仍允许写本阶段交付物与任务索引。既有授权不重复索取，运行环境或发布等额外授权遵守项目规则；handoff 记录授权，不产生授权。
- 标准阶段结束后停止。明确派发 quick 修复才可组合问题核对、最小实现、作者自审及验证；只读调查保持只读。没有整改就不生成 fix，已有任务仅缺验证就用 validate。
- 输入与索引冲突时核对，不能凭文件编号、修改时间或“最新”推断用户接受了方案。关键决定或候选无法确认时停止依赖它的工作，继续独立且已授权部分。
- 支持旧版独立交付和合并文件章节；缺模式时按标准理解，不补造前置文件。仅读取当前索引、直接输入及必要链接，复盘不是每阶段必读。

## 2. 决策与执行强度

- 事实、假设、建议和已确认决定分开。明确的局部用户修订记录确认来源、覆盖的旧条款、影响范围和验收变化，并让索引指向该记录；不追加设计追认。重要取舍、需求歧义或显著范围变化才返回 need/design，共享语义仍走项目治理。
- 改动范围、实现复杂度、风险与未知项决定设计/验证深度；文件数、行数和耗时不作机械门槛。事实不清先调查，一行高风险变化也可能需要升级。
- 执行者数量单独决定。默认单智能体，只有输入稳定、写入可分离、能独立验收且有并行收益时才建议分工；流程不自动授权启动其他智能体。
- design 确定审查方式、依据、复查责任与触发条件，以及 AC 对应的证据类型和执行前提。后续提高门槛需说明新事实与适用范围；同一作者切换阶段不构成独立审查。
- 视觉设计先说明方案数量、图片角色与用户待决定事项。默认一套方向的代表图，补充状态图只解决具体问题，生成图不能证明动态布局。修改同类组件要列影响实例、状态和明确保留项，覆盖截图外实例。
- review 区分确定缺陷、待核实问题、可选建议及是否阻塞。fix 区分认可判断与本次实施；可选项默认延后，纳入本次需说明必要性、范围及授权。
- 原作者优先整改，按既定条件增量复审：先核对候选关系和差异，再核查原 findings 与受影响断言。连续两次修复同一问题失败时重查根因、证据和测试假设。

## 3. 候选、证据与完成

- code/fix 保存候选清单和实现检查证据；后续阶段引用来源并核对适用性，不重抄指纹表。旧版清单沿用原来源，不回填历史。
- 优先固定 commit；允许未提交候选时记录基线、任务文件（含未跟踪文件）、精确差异及必要内容摘要。项目要求干净提交时不能用 handoff 代替，提交仍须授权。正式 review 不审查正在修改的工作区，使用固定提交或可复核快照。
- 业务候选与可变任务 README 分开核对。索引更新不等于业务变化，不对交付文档自身做递归摘要；保留无关工作区改动。
- validate 先判断证据缺口与前提。候选及相关环境未变时复用有效记录；证据矛盾、相关代码/配置/依赖/环境变化或用户明确要求时才重查。无关 HEAD 变化不触发全量检查；作者摘要不能代替必要的独立审查。
- 新增检查全部受阻时，只做最小候选核对，简短交付“待验证”、已有证据及恢复条件，不通过重复静态审查填满阶段。已有有效证据齐全时可据此判断验收。
- 分别记录检查通过、检查失败、未运行、环境受阻及整体验收状态。区分源码、编译、测试执行、运行、视觉和无障碍证据；环境导致构建失败时编译正确性未知。源码、生成图、提交均不能替代运行验收。
- 保存命令、工具、权限/沙箱、工具链、候选、关键错误、结果及恢复条件；区分基线失败与本次回归。另一工具接手后重查环境限制是否仍适用，不把单工具失败概括为仓库无法构建。同环境同原因连续失败两次后停止无依据的命令变体。
- 用户再次反馈失败时先核对源码、构建产物、诊断时间与复现条件，再决定是否修改。quick 从原始症状确定完成条件；编译诊断须在新候选的构建日志中核对，没检查 IDE 就不扩展结论到 IDE 或运行验证。
- 阶段结束、实现完成、作者自审、独立审查/复审、验收、提交发布状态分开。只有范围完成、必做问题关闭、所需复审完成且证据齐全时，才判定任务完成。
- 已授权提交成功后核对内容与原候选，串行更新索引的实际 commit 与提交状态。回填产生的文档改动如实报告，不为记录自身 commit 循环提交；历史交付不回写。

## 4. 落盘与共享写入

1. 实际执行才创建 `<阶段>-<轮次>.md`，各阶段独立编号，从 `01` 开始，至少两位，超过 99 不截断。选择未占用文件名，不覆盖其他执行者的草稿或结果。
2. 每份文件只有一个写入者。草稿标明“草稿／进行中”；一旦向用户报告交付或被下游引用即不可改写，修订新增轮次并引用原文件。
3. 使用 [交付骨架](../assets/handoff.md) 的五节：身份与输入、有效上下文、本阶段结果、证据与限制、下一步交接。记录实际 Skill 版本、协议、模式、阶段/轮次、执行者、实际时间、输入与候选；未知信息不编造。
4. 首轮保存必要上下文；后续重点写变化、影响、新证据和未决项，链接未变部分。关键结论、findings、必要文本证据进仓库；大日志与产物放任务 `scratch/`，临时路径不作唯一证据。
5. 首次 need/quick 按 [任务索引骨架](../assets/task-index.md) 建 README。已有索引仅合并本轮有效链接、候选、分开的状态、下一步、前提与负责人；不重复交付正文，不悄然替换已确认版本。
6. 先写并回读交付物，再串行更新任务索引并回读。更新前重读；同任务并行时指定唯一索引维护者，其他执行者交付待同步条目。所有权不明或冲突时保留阶段文件并报告“索引待同步”，不覆盖未知更新。
7. 不同任务分别维护目录，可独立推进；业务文件仍须明确写入所有权。普通阶段不改写项目根 `.cohestra/README.md`，避免跨任务争写公共入口。
8. 交付物写入失败报告“交接未完成”及错误、待写内容；部分写入和索引失败单独说明，不宣称事务回滚或全部成功。
9. 回复交付物绝对路径、结论、索引状态、必要待办和 `$cohestra <下一阶段>` 加准确输入。推荐下一步不等于执行授权。

## 5. 轻量交付与历史

- quick 正常修复写 code，有既有 review findings 则写 fix；实施前因需求或设计缺口停止，按实际进度写 need/design；实施中升级仍写当前 code/fix 并说明停止原因。
- 不生成 quick 文件或空白阶段文件。合并文件按实际覆盖职责写 need/design/code 或 fix/review/validate 章节；作者自审不冒充独立审查。有效索引可指向实际章节，如 `code-01.md#need`；合并章节不占独立阶段轮次。
- 已要求复审的 findings 可以标“已修复待复审”，不能因使用 quick 取消复审。升级时复用任务目录、候选和结论，只补缺少的工作，不扩大授权。
- 历史阶段和复盘保留原版本与事实。规则升级不自动接受方案、降低验收或重跑任务；仅处理当前任务的明确冲突。新的流程改动另行指派，普通阶段不改写技能。
