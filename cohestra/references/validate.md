# validate

通过 $cohestra validate 调用；与 [公共流程](workflow.md) 一起执行。

## 调用

```text
$cohestra validate
.cohestra/handoffs/<task-slug>/review-01.md
```

已有有效候选、只缺证据时，直接给任务目录或 code/fix 交付：

```text
$cohestra validate
.cohestra/handoffs/<task-slug>/code-01.md
```

## 输入与职责

输入为任务目录、最终候选的 review，或按既定要求无需复审的 code/fix。读取有效验收条件、候选来源和适用证据。业务候选只读，允许在已有授权内补验证、写验收交付和任务索引，不自行修复或改写验收要求。

## 本阶段工作

1. 先核对准确候选、有效 AC 和必须处理的 findings，确认已有独立审查与检查记录的适用性。以 code/fix 的候选清单为来源，不复制整张指纹表。
2. 列出本轮新增证据、可执行检查及缺失前提。候选与相关环境未变时复用有效记录；证据矛盾、相关变更或用户明确要求时才重查，不能以作者摘要代替项目要求的独立审查。
3. 若新增检查全部缺少前提，完成最小候选核对后写简短待验证记录，引用已有结论和缺口；不重复静态审查填满阶段。证据已齐全时仍可基于有效记录完成验收判断。
4. 对可执行的缺口按 AC 补证据。分别记录检查通过、检查失败、未运行或环境受阻，区分源码、编译、测试执行、运行、视觉和无障碍；构建被环境阻断时编译正确性仍未知。
5. 再次反馈失败时先核对源码、产物、诊断时间与复现条件。确认验收失败优先给出证据并建议 fix/design/need；尚未确认失败而缺必要复审时，复审输入、授权与执行条件齐备则写 `acceptance.status: pending`、`next: {stage: review, allowed: true, reason: stage_completed}`。仅缺本阶段可补且条件齐备的验收证据时才允许 `next.stage: validate`；必要输入、权限或执行条件不足时按公共流程走 blocked。正文推荐与结构化出口一致，不自行复审、整改或降低验收要求。
6. 给出已完成、待验证或未通过，并列出下一步、负责人或待指派、缺失前提。只有范围完成、必做问题关闭、要求的复审完成且必要证据齐全时，才判定任务完成。

本阶段结果写 AC → 证据来源/本轮新增证据 → 通过/未通过/未验证，注明环境受阻原因；复用项只引用，不重写原报告。分别报告整体验收和实现、审查、提交状态。验收判断给出结构化状态 `acceptance.status`（passed / failed / pending / blocked），写入交付物与任务 README Front Matter（见 [公共流程](workflow.md) 第 7 节）。满足本节完成条件才判 passed；本轮判为 passed 后，必须按公共流程第 7.3 节联合写入并校验任务 completed 及其余完成字段，不能仅记录验收通过而保留任务进行中。全部受阻时五节可各用短句完成。

## 交付与停止

新增 `validate-<轮次>.md`；骨架字段、落盘顺序、索引同步与停止规则见 [公共流程](workflow.md)。

对口 verify：不适用——本阶段是整条链的最终验证关口，交付后不提议 verify；需要单独核对证据与 AC 的对应（如未验证项被写成通过）时由用户主动调用，发现偏差时回相应阶段，不改写验收记录。

范围完成、必做问题关闭、要求的复审完成且必要证据齐全时交付完成结论；否则推荐相应阶段并说明缺口、前提与负责人。最终回复分别说明验收结论与完成状态同步结果；本轮验收通过但索引同步失败时，按公共流程第 5 节报告「验收通过，完成状态待同步」，不宣称状态已同步。验证完成不自动授权提交或发布。
