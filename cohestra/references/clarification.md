# 共用需求澄清规则

进入 need 或 design 时读取；澄清是这两个阶段的工作方式，不是独立入口或阶段。阶段职责、业务只读边界、交付和停止规则仍由对应阶段及[公共流程](workflow.md)规定。

## 调查与提问

1. 先只读调查，再提问。能从代码、文档、日志、接口或截图查证的事实自行核实；先把用户提出的方案与真正目标分开，只询问会实质影响需求或方案、且现有材料无法确定的问题。
2. 按决定的依赖关系组织问题，先解决上游问题，再根据回答调整后续问题。每轮最多 3～5 个关键问题，允许更少或不提问；不为凑数量或轮次追问。
3. 每个问题提供有意义的候选选项、推荐方案、简要依据及必要取舍；无依据推荐时明确证据缺口，不强行给出结论。
4. 保留已有有效决定和授权，记录来源，不重复询问已确认事项。新的回答只修订受影响部分，不重开无关决定。
5. 区分已验证事实、已确认决定、待验证假设和待决定问题。低影响且容易逆转的细节可以采用明确标注的默认值；不得覆盖用户决定、改变关键范围或扩大授权。
6. 必须通过原型或实验判断的问题，记录假设、验证方法和所需证据，不用追问代替验证。验证动作遵守本阶段的范围和授权；未获得证据前不写成已验证结论。

## 关键决定未答复

关键决定指会实质影响目标、范围、验收、授权或重大方案取舍的决定。

- 没有既有决定或明确代决授权时，未答复及“就这些”均不表示接受尚未确认的推荐。停止依赖该决定的工作，继续独立且已授权部分；不能把关键决定改标为假设来继续推进。
- 用户不再补充时停止重复追问，保留未决项及影响。已有明确代决授权时可在授权范围内作出决定，记录授权来源、选择及依据，不把代决写成用户逐项确认。
- 必须结束当前阶段且仍缺必要关键决定或下节所需的整体确认时，按公共流程第 7 节的既有受阻路径交付：`stage_result.status: blocked`、任务 `status: blocked`、`blocked: {value: true, reason: human_decision_required}`、`next: {stage: null, allowed: false, reason: human_decision_required}`。不报告阶段完成，也不允许进入下一阶段。
- `unattended` 不执行交互提问；缺少必要人工决定时直接受阻，按公共流程第 7.4 节停止，不切换为交互模式等待。

## 收敛与确认

关键问题收敛后，在对话中给出可通读的完整汇总，覆盖目标、范围、约束、关键决定、未解决事项和验收标准，并标明本轮采用的默认值、假设及待验证事项。need 汇总完整需求；design 同时汇总所选方案、重要取舍和执行／验证计划。可以附正式文档，不只给链接或让用户自行拼合历轮问答。

1. 请用户通读并明确认可这份整体需求／方案。单项决定均已回答仍须整体确认，但不重问已确认的单项。整体确认前仅提供待确认汇总或草稿，不报告本阶段完成，不把本轮索引发布为允许进入下一阶段；必须结束或正式交付时按上节受阻路径处理。
2. 按上下文判断答复是否明确认可当前整份汇总，不要求特定口令；沉默、结束追问或仅要求交付文档不等于整体认可。记录确认对象、对应内容及答复来源。若同一完整汇总已获明确认可且无实质新增或修改，引用原汇总与确认来源，不重复确认；既有阶段 completed 本身不证明发生过整体确认，也不据新规则回填历史。
3. 用户更正目标、范围、约束、关键方案、验收或影响这些内容的默认值／假设时，给出更新后的完整汇总并突出变化，再核对整体认可；用户已明确接受包含这些修订后的整体时，不重复索取同一确认。纯排版或等价措辞整理不重开确认。
4. 代决授权与免除整体确认分开判断。“帮我选”“无需逐项确认”等普通代决授权不免除最后整体确认；只有用户明确免除本次最终整体确认时，才可在授权范围内直接定稿，并保留完整汇总及该指令的来源和范围。免除整体确认也不自动授予未决关键取舍的代决权。

按当前阶段判断是否具备下一步前提，区分可保留的验证项与阻塞推进的决定；在 handoff 记录整体确认来源或明确免除指令及采用范围，不新增协议字段。整体确认与实施授权分别判断：需求或方案确认不自动授权实现；既有明确实施授权继续有效，不重复索取，但不能用它替代未获认可的整体汇总。
