# 本机资料与正式文档

## 存储边界

`.yuzio/` 是当前工作区的本机执行资料，不是项目正式文档或 Git 备份。Cohestra 在 `.yuzio/cohestra/` 保存入口、任务索引、阶段 handoff、复盘及证据；本机记录仍须持久化和保留，不能因被忽略就视为可丢弃缓存。Git 不备份未跟踪的本机资料。

首次写入及复用容器前，检查工作区根 `.gitignore`，最小追加 `/.yuzio/`（已有效覆盖时不重复），保留其他规则。初始化和阶段写入包含这项维护；纯只读调查与 report 不修改任何文件。检查规则实际生效及 `.yuzio` 是否已有被跟踪文件；已有跟踪不受忽略规则影响，只报告清单，不自动移出索引、暂存或提交。显式反向规则、项目要求跟踪资料、并发修改或无法写入时报告冲突，不强制覆盖；忽略尚未生效时不继续写本机资料。非 Git 的存储位置无需创建 `.gitignore`。

容器模板中的 `.gitignore` 以 `*` 作为防误收兜底，仍须维护项目根规则。根规则带前导 `/`，只覆盖工作区根的资料目录，不误忽略嵌套测试夹具。安装技能不修改业务项目。

## 正式文档

需求、设计、ADR、接口说明、操作手册、正式验收结论等需要随代码共享和长期维护的文档，写入项目已有文档目录及其分类；无既有约定时使用 `docs/` 下与内容匹配的位置。产品配置和团队约束保留在项目原有真源；本机入口只保存引用和执行配置。

每轮先依据任务目标、交付用途和适用项目规范判断是否需要新增或更新正式文档，需要时作为本轮交付自动完成，不等待用户另行说“整理文档”或“保存到 docs”。任务本身需要可供开发/使用的说明，或项目规范要求同步需求、设计、接口、操作说明、验收记录时，均构成整理依据；例如修订接口时同步既有接口文档，无需再次确认。优先更新对应的现有正式文档，补齐必要附件与引用，避免另建重复版本。

阶段 handoff 是执行记录，不因名为 need/design/validate 就自动成为正式文档。没有正式交付需要的局部修复、调试和阶段过程留在本机，不机械复制所有 handoff，也不为每个任务新建一套文档。正式文档以项目目录中的版本为真源，本机索引记录路径与版本。目录可按已有约定或 `docs/` 确定时直接执行；只有缺少影响内容正确性、任务范围或业务决定的关键信息且无法从现有上下文确定时才澄清，不单为是否整理、保存位置或补附件重复询问。

正式交付必须能够脱离 `.yuzio` 阅读：有效决定、验收范围、结论、遗留和必要证据摘要保存在正式文档内；所需图片/附件放入项目已有文档资源目录或可持久访问的明确位置。不得仅链接 `.yuzio`、临时路径或本机绝对路径作为依据。保留待决与未验证事项，不把归档当作批准、验收通过、提交或发布。阶段对业务实现或候选的只读限制，不排除自动整理本阶段应交付的正式说明或报告；不得借整理改写被审查/验收的候选、业务决定或验收要求。`init`、纯只读 `report` 不因此扩展为文档整理入口；用户明确“只讨论”“不落盘”或限定输出范围时遵守其限制。
