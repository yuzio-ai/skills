# closeout · 单任务收尾编排

通过 `$cohestra closeout` 明确调用；与[公共流程](workflow.md)一起执行。此入口串行编排独立 review、必要 fix、复审和收尾。默认以 validate 验收最终候选，可显式选择在独立 review 完成工程交付。

## 调用与范围

在完成任务的原会话中可直接调用：

```text
$cohestra closeout
```

也可指定目标：

```text
$cohestra closeout
项目：<项目绝对路径>
任务目录：<已有任务目录绝对路径>
范围与验收依据：<仅补充原任务未包含的必要信息>
终点：工程交付
```

- 未附任务目录时，优先接续本会话已明确的任务；项目、任务、基线、验收依据或变更归属无法唯一确定时才澄清。此入口自行选择本任务的实际交接输入，不按六阶段链条猜一个“上游最新文件”。
- `终点：工程交付` 是可选项。新调用省略时走默认整体验收。派发前核实用户选择、当轮必做检查及验收依据。逐项记录后续验收的范围和负责人，无待办时写明无。仍属本轮硬门槛的检查应先落实执行条件。缺授权或输入时报告缺口和恢复条件，未经用户明确确认不得移出当轮范围。
- 沿用原任务与有效决定。原会话此前未使用 Cohestra 时，以已确认需求、实际变更及可核实基线首次从 review 建立任务索引；缺容器先最小初始化，不补造 need/design/code 历史。已有任务缺资料或契约不合法时按公共流程恢复，不能另建替代任务。
- 本次调用授权必要的独立 reviewer、范围内必做整改、复审、已有权限内的验证及必要交付。当前有效的任务级只读限制、明确保留项、运行环境授权和项目规则继续有效，用户本次明确变更的限制以本次为准；review 本阶段的业务只读不延伸为 fix 禁止整改。不能由“收尾”推导可选优化、全库清理、新功能、提交、推送、发布或停止其他任务的权限。
- 不创建或修改 `.yuzio/cadra`、队列、Task 或 Run，不要求安装 Cadra。目标若正被 Cadra 或其他会话占用，或相关执行活性未知，停止冲突部分，不接管。已结束的历史 Run 与交付保持原样。

## 执行者与交接

- 主会话负责串行编排，可承担 worker 的 fix/validate；原作者可用时优先由其整改。需要执行 review 时创建独立 reviewer 子 agent，核实其实际身份与所有被审实现／整改作者分离；初审与复审优先复用该 reviewer。缺少必要子 agent 能力、身份无法核实或旧执行者／工具尚未确认停止时，报告缺口，不改为作者自审后宣称独立审查通过。仅复用已通过的完整记录时不创建闲置 reviewer。
- 给 reviewer 干净上下文，只传本次实际技能目录与版本、任务目录、有效需求／决定／授权、项目规范、固定候选、必要依赖、findings 和证据；不继承完整作者聊天。普通阶段子 agent 不再委派、不自行启动下一阶段。closeout 的主会话不作为 reviewer 后再修复同一候选。
- 每次进入阶段时读取对应说明，明确本次为 closeout 派发、实际角色、目标阶段、候选及必要复审要求。工程交付同时传递经核实的终点、必做检查、待办与确认来源。若主会话刚完成最小初始化，将实际初始化动作与执行者交给首轮 reviewer。阶段执行者在既有 handoff 记录本次派发来源、实际身份及适用的初始化信息。
- 同任务同一时刻只运行一个阶段，由该阶段执行者独占发布 handoff 与任务索引；主会话承担 worker 时仅在自身阶段内发布。前一阶段及其工具已停止、[索引发布](publication.md)成功并回读核实后，才移交写入权。主会话核对实际交付、轮次、身份、候选、覆盖与完整契约，不能只凭 agent 摘要或可读取的 `next` 推进。
- review 的业务候选保持固定，所需未修改依赖也须可复核。核实本任务基线、精确差异、未跟踪文件及删除路径；共享工作区总 diff 不代表本任务归属。其他会话的写入不得静默混入候选或使旧证据继续有效。

## 阶段推进

首次执行从独立 review 开始；已存在适用的独立 review 时，先核对范围、候选、作者分离及文档／清理覆盖，可复用后按有效 `next` 继续。用户要求重审时新增 review 轮次。恢复时先处理已完成但未同步的交付，避免重跑；不得以原任务曾 completed 或作者曾检查为由省略本次所需证据。

默认整体验收时，若任务已在 review 结束但尚无最终候选的有效验收，本次 closeout 授权核实独立 review 后继续 validate，保留旧交付及原 `next`。工程交付可复用满足本次[工程终点条件](review.md#工程交付终点)的终态 review，或同候选已有适用的完整验收。已有 review 仍建议 validate 时，保留原交付。确需在新终点形成工程完成状态时，由独立 reviewer 基于已有证据核对本次明确调整的终点、必要检查及待办，实际交付新的 review 轮次。未解决的已知验收失败和仍有效的受阻前提按原出口处理。

最终候选已有适用的独立 review／复审和 validate passed，且收尾条件仍成立时，直接复用记录。用户明确要求重新检查的范围按本次授权执行。

| 当前结果 | 编排动作 |
|---|---|
| review 覆盖齐备且无必做问题 | 默认进入 validate。工程交付由 reviewer 按工程终点条件发布后进入收尾 |
| review 有必做问题，且整改在授权内 | worker 执行 fix，再由独立 reviewer 执行 review 复审；按差异核查原 findings 和受影响路径 |
| review 必要覆盖有缺口 | reviewer 先在已有授权内补查；缺输入、权限或执行条件时按原 blocked 出口停止，不以零 findings 放行 |
| fix 已完成 | 必须独立 review，不能直接验收；新的业务候选重新核对适用证据 |
| validate 确认失败 | 按有效 next 在范围内 fix，再独立复审及验收；若需 need/design 或新产品决定，停止并交回用户 |
| validate 为 pending | 仅按已核实的 review／validate 出口补必要复审或可执行证据；条件缺失时受阻，不空转 |
| validate 通过且索引同步成功 | 执行下节收尾核对，满足条件后结束本次编排 |

各阶段按公共流程第 7 节发布契约。默认终点需要最终候选 validate 通过，工程终点需要独立 review 按用户声明的终点完成。每次 fix 都明确传递独立复审要求，由实际阶段执行者发布其结果。

文档与清理使用[既有规则](review-coverage.md#文档同步与替代内容清理)：在 review 检查行为／文档同步和被替代代码、入口、配置、测试、文档的用途，在 fix 完成必要整改，最终 review 与 validate 覆盖整改后候选。删除须核实实际使用关系，不能仅凭搜索无引用。范围外与可选项列为遗留，不自动实施。

## 停止与恢复

- 用户停止、阶段受阻或不可重试失败、授权／候选冲突、索引同步失败时不启动后续阶段；先核实本次 agent 与工具状态，保留真实交付与恢复依据。索引同步失败沿用发布细则的原文信号，不因后续摘要而省略或声称全部完成。
- 一次 closeout 授权默认最多 12 次阶段调用、其中最多 3 轮 fix；同一阶段的失败重试最多一次，且须原因已解除或有新的有效依据，无依据不重复。首轮有效上下文记录本次授权、起始交付与预算，后续引用；实际进入阶段即计次，失败及中断的调用也计入，复用已有证据和仅恢复索引不新增调用。中断时保留实际派发及执行证据，无法核实是否执行则先核对，不盲目重放；续接不因重建任务或换 reviewer 重置。用户可明确调整预算。仅编排预算耗尽时，保留最后真实阶段的契约与合法 next，记录暂停原因、遗留和恢复条件，不伪造一个 blocked/failed 的工程阶段或新增控制状态。
- 继续中断的 closeout 时，先确认此前执行者和工具已停止，核实有效索引、实际 handoff、候选、角色、已记录的终点及剩余预算。已完成但索引待同步时先恢复同步。调整终点或追加已耗尽的预算须有新的明确授权。

## 收尾与交付

收尾是本入口的最后核对与交付，使用既有 handoff 和任务索引。终点、范围、预算与来源保存在首轮 handoff 的有效上下文，后续 handoff 引用。最终 validate 或工程终点的 review 在发布前记录候选、文档／清理、必要证据及遗留。发布回读、工具停止和临时清理的结果在最终回复报告。

1. 核对最终候选及必要依赖仍匹配独立 review／复审与本终点所引用的证据，必做问题已关闭，文档同步及替代内容处理有据可查。若候选漂移，保留原结论并报告变化来源。只在归属与授权已确认时重新固定候选、执行必要复审及验证。
2. 回读最后 handoff 与任务 README，确认与实际发布结果及公共流程第 7.3 节的终点一致。完成后若有新业务整改，重新固定候选并按实际终点进入整改、复审与验证。正式说明或报告按[存储约定](storage.md)交付。
3. 确认本次角色与工具停止。仅按[日常留存](retention.md#日常留存)移除本次拥有、无引用且无恢复用途的临时提案；保留 handoff、候选及被引用证据，不启动历史资料清扫。
4. 最终回复给出任务索引及必要交付的绝对路径、最终候选、独立审查／整改、工程交付、整体验收结论、索引同步和人工待办。条件未满足时明确受阻项及恢复输入。工程完成后的补验可在取得所需授权或同候选新证据后显式调用 `$cohestra validate`。
