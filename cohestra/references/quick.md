# quick

通过 $cohestra quick 调用；与 [公共流程](workflow.md) 一起执行。quick 组合六阶段职责，不是第七阶段。

## 输入与职责

输入为原始问题、预期与参考材料，或已有任务目录/handoff。只有明确派发轻量修复才连续实施；只读排查保持只读。新任务核对无同目标记录后才建目录。已有 findings 时读取原 review、候选与复审要求，不因切换模式取消关口。

## 适用判断

先做必要的只读调查，记录以下判断及依据：

- 预期行为有明确需求或规范依据，不需要新的产品决定。
- 根因有证据支持，修复路径清楚；不能将未经核实的猜测当作定位完成。
- 影响局部，没有重要方案取舍、复杂状态或跨模块联动。
- 不改变契约、权限、持久化、迁移等关键语义，风险较低。
- 有明确的验证方法；缺少必要环境或授权时可保留待验证，但不降低验收标准。

文件数、代码行数和预计耗时仅供参考。一行高风险改动也需升级。无法满足条件时按下面的升级规则交接，不以“轻量”为由继续扩大实施。

## 执行步骤

1. 检查输入确认状态、工作区、基线及文件所有权，保留其他任务改动。已有任务复用有效结论；只需补验证时推荐 validate，不重复修复。用户再次反馈失败时，先核对源码、构建产物、诊断时间与复现条件，再决定是否修改。
2. 从原始症状确定现象、预期、范围和完成条件，保留已有 AC ID，新条件使用新 ID。编译诊断类问题需核对目标诊断在对应新候选的新构建日志中是否消失；没有检查 IDE 时，结论仅覆盖已查证的命令行诊断，不自动扩展到 IDE 或运行验证。
3. 记录根因证据、最小方案、影响的组件/状态及明确保留项、验证方法和审查/复审安排。同类组件核对截图外实例。明确的局部用户修订记录确认来源、覆盖条款和验收变化，不额外索取设计追认；重要取舍、歧义或显著范围变化按升级规则处理。
4. 完成必要实现和相称测试。处理既有 findings 时逐条裁决接受、不接受并给依据、待确认或延后；区分认可问题与本次实施，可选项纳入需记录必要性、范围及授权依据。
5. 作者自审实际差异、异常路径和受影响断言，修复本次引入的问题。连续两次修复同一问题失败时，重查原因、证据与测试假设，不盲目追加尝试。
6. 先判断新增证据缺口及执行前提，再执行相关检查与项目门禁。复用仍适用的记录；证据矛盾、相关变更或用户明确要求时才重查。新增检查全部受阻时，做最小候选核对并简短记录待验证，不重复静态审查填满验收；证据已齐全时可据此完成判断。逐项区分通过、失败、未运行、环境受阻，环境受阻时编译正确性仍未知；源码、编译或生成图不代替运行验收。
7. 在本轮交付物中保存可复核候选及证据来源。优先引用明确 commit；允许未提交候选时记录基线、任务文件（含未跟踪文件）、精确差异与必要摘要，不自行提交。后续引用清单核对适用性，业务候选与可变索引分开，不对文档自身做递归摘要。
8. 形成合并交付，分别说明实现、审查、整体验收及提交状态。作者自审不构成独立审查；已修复但要求复审的 findings 记为已修复待复审。只有范围完成、必做问题关闭、要求的复审完成且必要证据齐全时，才判定任务完成。

## 升级与停止

| 触发情况 | 后续处理 |
|---|---|
| 预期有争议、需求歧义或显著范围变化 | 转 need；明确授权的局部修订只登记覆盖关系 |
| 存在重要方案取舍、复杂状态或模块联动 | 转 design |
| 风险升高或项目要求独立审查 | 按授权完成允许的工作，固定候选后转 review |
| 涉及共享契约或关键语义 | 停止相关实施，进入项目规定的治理流程 |
| 同一问题连续两次修复失败 | 重新核查原因、证据与测试假设，再确定下一步 |
| 必要检查暂时无法执行 | 记录具体工具、环境限制与恢复条件，待条件具备后补 validate；无需重跑实现 |

如项目规定审查必须先于实施，到该关口即停止；独立审查是实施后的关口时，可先完成已授权修复，再交接 reviewer。不得取消既定审查要求或自行启动其他智能体。

升级记录触发原因、已有结论、已修改内容、准确候选、剩余工作及下一步的文件/章节引用。复用同一任务目录和有效结论，只补缺少的工作，不重跑整套流程。升级不扩大授权，依赖未决决定的工作停止，其他独立且已授权的部分可以完成。

## 落盘与交接

1. 正常修复写 `code-<轮次>.md`；针对既有 review findings 整改写 `fix-<轮次>.md`。实施前因需求不明确或进入设计条件不足而停止，写 `need-<轮次>.md`；需进一步设计或明确审查安排时写 `design-<轮次>.md`。治理阻止实施时按实际调查进度选 need/design，链接缺口。实施中升级仍写当前 code/fix，注明未完成及停止原因。
2. 各阶段独立编号，从 `01` 开始、至少两位，选择未占用的文件名；交付后修订新增轮次，不覆盖旧文件。不创建 `quick-01.md` 或空白阶段文件，合并章节不单独消耗阶段轮次。
3. 保留“身份与输入、有效上下文、本阶段结果、证据与限制、下一步交接”五节，可用短句和链接。注明 cohestra v0.3、实际 Skill 发行版本、轻量模式、适用依据与实际覆盖职责、任务/阶段/轮次、执行者、实际时间、状态、输入及候选来源；未知不编造。首次写必要上下文，后续重点写变化、影响、新证据和未决项。
4. “有效上下文”保留目标、范围、有效决定及确认来源、授权停止线和必要链接。“本阶段结果”按实际工作使用以下三级标题；未执行的工作不创建空节或宣称完成：
   - `### need`：现象、预期、范围、AC 与确认来源。
   - `### design`：根因证据、最小方案、影响范围及审查/复审安排。
   - `### code` 或 `### fix`：实际改动、候选与偏差；fix 包含 finding ID → 裁决 → 修改/延后 → 证据 → 修复/复审状态。
   - `### review`：标注作者自审、覆盖范围、结果与剩余问题，不冒充独立审查。
5. 在“证据与限制”下使用 `### validate`，记录 AC → 证据 → 通过/未通过/未验证及具体待办，另注明检查未运行或环境受阻。关键结论与必要文本证据写入仓库；大日志、缓存和产物放任务 `scratch/`，临时路径不能是唯一证据。
6. 写入并回读交付物后，串行更新 README 的目标、模式、当前执行、索引维护者、候选、有效链接、待确认/被取代版本，以及下一步、缺失前提和负责人。实现、作者自审、独立审查与复审、验收、提交状态分开记录；不要求独立审查时注明依据。
7. 有效需求、设计、自审和验收可链接 `code-01.md#need`、`code-01.md#design`、`code-01.md#review`、`code-01.md#validate` 等实际章节；文件名按实际交付替换。合并文件只登记一次，保留有效前序链接，不按编号或时间自动接受新结论。
8. 索引更新前重读；并行时唯一维护者更新，其他执行者回报条目。所有权不明或冲突时报告“索引待同步”，不覆盖未知更新；模式变化写明依据，不回写历史。文件写入失败报告“交接未完成”及待写内容。
9. 已授权提交成功后，核对内容并回填索引的实际 commit 与提交状态；回填产生的文档改动如实报告，不为编号循环提交。quick 不因此获得提交授权。
10. 最终回读确认后回复交付物绝对路径、结论、索引状态及必要待办，不复述整份文档。

## 下一步

完成且证据齐全时交付后停止；待验证转 `$cohestra validate`，需审查或复审转 `$cohestra review`，需求或设计缺口转对应阶段。每次附合并交付物的准确路径或任务目录、剩余证据和前提；不自动启动下一阶段。
