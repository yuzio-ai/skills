# review

通过 $cohestra review 调用；与 [公共流程](workflow.md) 一起执行。

## 调用

```text
$cohestra review
.cohestra/handoffs/<task-slug>/code-01.md
```

## 输入与职责

输入为任务目录或 code/fix 交付，读取有效需求/设计、固定候选、前次 findings 及复审要求。业务文件只读，允许在授权范围内做审查检查、写审查交付与任务索引，不自行修复。

## 本阶段工作

1. 从 code/fix 来源核对固定候选；工作区正在变化时读取固定提交或可复核快照，无法固定则报告缺口，不形成正式结论。
2. 从源码与实际路径独立核查需求、设计、正确性、异常路径、状态交互及必要测试，允许质疑设计。
3. 作者摘要与 PASS 不是独立证明；执行必要的针对性检查。已有独立检查可核对来源、候选与适用范围后引用；不以重复验证代替独立判断。
4. 首次覆盖相关范围；复审先证明候选关系和差异边界，再检查原 findings、修改影响及受影响断言，有新依据才扩大范围。
5. 问题记录稳定 ID、类型、严重度、阻塞性、位置、触发条件、后果、依据和验证方法；区分确定缺陷、待核实问题与可选建议。
6. 可选建议不自动进入 fix；标明原有问题或新回归，无问题仍说明范围与证据限制。明确用户修订的授权与覆盖关系，不把缺少额外设计追认当作授权缺失。
7. 记录实际审查者和方式，同一作者换阶段不构成独立审查。保持既定复审要求；列出下一阶段剩余证据、可执行条件及缺失前提。

本阶段结果写候选核对、审查范围和方式、findings/复审状态、证据边界、剩余检查及前提。项目要求独立报告时另存并链接。

## 交付与停止

在原任务目录新增 `review-<轮次>.md`，采用 [交付骨架](../assets/handoff.md)，按公共流程落盘、回读并串行同步任务索引。

对口 verify：review 本身就是 code、fix 的正式验证关口，交付后不提议 verify。需要先做偏差核对再定审查范围时，可在 review 前由用户主动调用 `$cohestra verify`。

必做整改转 fix，否则转 validate。列出剩余证据、可执行条件、缺失前提和负责人；全部受阻时只需最小核对与简短待验证交付。下一步使用 `$cohestra <阶段>` 加本轮交付物或任务目录与补充指令；交付后停止，不自动执行下一阶段。
