# review

通过 $cohestra review 调用；与 [公共流程](workflow.md) 一起执行。

## 调用

```text
$cohestra review
.yuzio/cohestra/handoffs/<task-slug>/code-01.md
```

## 独立审查与委派

单独调用 `$cohestra review` 或按目标自动选择本阶段时，默认授权主会话委派一个独立 reviewer 子智能体，不需另行请求启动许可；仅讨论规则不触发执行。这只授权本轮 review，不授权 fix、validate 或 closeout。

- 主会话核对目标项目、任务、有效输入和固定候选，完成必要的最小初始化后派发；它负责交接与核对交付，不替 reviewer 出具审查结论。reviewer 必须与所有被审实现／整改作者分离，以实际 agent 身份及来源核实，不以角色名称或作者切换阶段代替。复审优先复用仍满足身份与上下文条件的原 reviewer；不可用时创建新的独立 reviewer，并传递原 findings 与候选差异。
- reviewer 使用干净上下文，不继承完整作者聊天；只传实际技能目录与版本、目标项目和任务目录、有效需求／决定／授权、项目规范、固定候选及必要未修改依赖、上游交付、findings 和证据。作者摘要只作为线索，reviewer 独立读取原始证据。
- 派发时明确主会话身份、实际 reviewer、调用来源为单独 review、本轮候选和阶段边界。reviewer 读取本阶段规则并独占写入本轮 handoff 与任务索引；主会话等待其结束，回读核对候选、实际身份、结论及索引同步，再汇报并停止。主会话不并行修改索引、不代写 reviewer 结论；索引同步失败沿用[发布与恢复](publication.md)，不重跑审查或覆盖未知更新。
- 已收到单独 review、closeout 或 Cadra 明确派发的 reviewer 直接执行，不再创建子 agent、不启动下一阶段。收到派发不能只凭声称的角色放行，仍须核实实际身份与作者分离；Cadra 和 closeout 分别沿用下方已有派发规则。
- 缺少子智能体能力、身份无法核实或无法固定候选时，按公共流程既有 blocked 出口停止，不静默退回主会话自审。尚未成功派发时，主会话可如实记录受阻交付及索引，执行者写自身，注明独立审查未执行；已派发但执行／停止状态不明时，先核实，不争写索引或另起 reviewer。候选、身份、工具缺口分别按实际原因使用 `candidate_unavailable`、`missing_input`、`dependency_unavailable` 等既有 reason，不新增控制字段。
- 用户明确要求本次不委派或只做作者自审时，记录该指令与实际审查方式，不宣称独立审查。若项目或既定验收仍要求独立证据，保留缺口；不能以本次例外免除既定门禁。工具不可用、超时或预算不足不属于用户明确例外。

以上仅改变本入口的默认执行方式；协议仍为 0.8，不改历史审查记录，也不从历史阶段名推断独立身份。

## 输入与职责

输入为任务目录或 code/fix 交付，读取有效需求/设计、固定候选、前次 findings 及复审要求。业务文件只读，允许在授权范围内做审查检查、写审查交付与任务索引，不自行修复。

Cadra 派发时按[编排派发](workflow.md#编排派发)核对 reviewer 绑定及实际身份，确认未承担本任务实现或整改。首次评审读取明确交付和必要原始证据，不继承作者的完整聊天；复审优先沿用原 reviewer。身份无法核实或候选正在变化时报告受阻，不把作者自审当作独立评审。记录实际 reviewer、候选和本次调用来源，阶段结束后由 Cadra 决定后续派发。

[closeout](closeout.md) 派发时按其单任务角色规则核对独立 reviewer、固定候选与调用来源；业务只读和本阶段发布后停止的边界不变，后续由 closeout 主会话安排，不套用 Cadra 资源协议。

## 本阶段工作

1. 从 code/fix 来源核对固定候选，按[公共流程第 4 节](workflow.md#4-候选证据与完成)确认可复核性；候选无法固定时不形成正式结论。
2. 按 [风险覆盖](review-coverage.md) 记录适用风险、真实调用路径、固定候选证据与缺口；从源码与实际路径独立核查需求、设计、正确性、异常路径、状态交互及必要测试，允许质疑设计。作者摘要与 PASS 不构成独立证明；执行必要的针对性检查，已有证据先核对来源、候选和适用范围。
3. 首轮独立核实[业务交付前的风险检查](review-coverage.md#业务交付前的风险检查)中适用的生产入口、生命周期终态和替代路径。复审先核对候选差异，再按[复审证据要求](review-coverage.md#缺口和复审)检查原 findings 和受影响断言，有新依据才扩大范围。
4. 每项 finding 记录稳定 ID、类型、严重度、阻塞性、位置、触发条件、后果、依据和验证方法；按公共流程区分确定缺陷、待核实问题与可选建议，标明原有问题或新回归。
5. 记录实际审查者、方式、覆盖范围和证据限制，列出剩余检查、复审状态及前提。无问题也说明范围和限制；项目要求独立报告时另存并链接。
6. 将未关闭 findings 计数（blocking / non_blocking，必要时 unresolved）写入交付物与任务 README Front Matter，字段和出口按公共流程第 7 节。

## 交付与停止

新增 `review-<轮次>.md`；骨架字段、落盘顺序、索引同步与停止规则见 [公共流程](workflow.md)。

确定缺陷按必做整改转 fix。必要覆盖缺口先在本阶段补查，缺输入或授权时交付 blocked，零 findings 不能补足覆盖。覆盖齐备且无必做整改时，按既有规则推荐 validate 或发布已声明的终点。列出剩余证据、可执行条件、缺失前提和负责人。

适用时必须按 [文档与清理要求](review-coverage.md#文档同步与替代内容清理) 独立核对文档和实际行为，以及旧代码／入口／配置／测试／文档的有效用途。Cadra 收尾评审覆盖提供的跨任务增量；权限、候选和必要证据不足时按原出口受阻。

### 工程交付终点

仅在 closeout 或普通 Cadra Task 明确传入用户已确认的工程交付终点时使用。核对终点来源、当轮必做检查与延后验收的范围和负责人。独立核对最终固定候选及必要依赖、实际结果与原始证据，逐项确认必做检查覆盖且通过。fix 后须复审最终候选。未关闭必做问题走 fix，仍适用的已知验收失败按原整改或恢复路径处置。缺必需证据、审查身份、候选或执行条件时按既有受阻出口说明恢复条件。

满足条件后，在 `review-<轮次>.md` 记录决定来源、必做检查及适用结果、原生等后续待验项和负责人。按[用户声明的终点](workflow.md#73-next-标准化)发布 `status: completed`、`stage_result: {stage: review, status: completed, round: 本轮轮次}`、`next: {stage: null, allowed: false, reason: task_completed}` 和 `blocked: {value: false, reason: null}`。没有适用于当前候选的正式验收结论时省略 `acceptance` 或写 null。引用适用的正式结论时保留其来源、范围和候选。本轮 review 的工程完成本身不生成验收通过。按[发布规则](publication.md)校验并回读，索引未确认同步时停止收尾。
