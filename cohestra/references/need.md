# need

通过 $cohestra need 调用；与 [公共流程](workflow.md) 一起执行。

## 调用

```text
$cohestra need
需求：<目标、范围、约束和参考>
```

## 输入与职责

输入为原始需求及参考材料，或已有任务目录/handoff。首次任务先核对没有同目标任务，才建立任务目录；需求修订复用原目录。业务文件只读，允许写需求交付与任务索引。

## 澄清提问

读取并执行[共用需求澄清规则](clarification.md)。本阶段重点是目标、优先级、范围、边界与验收，不把用户提出的实现手段直接写进 AC。优先核对：

- 目标：解决谁的什么问题，现状如何，怎样算成功。
- 分解：是否属于更大目标，本次做到哪一步。
- 边界：明确排除项，以及必须保留的既有行为。
- 验收：哪些现象证明完成，由谁判定、在哪里验证。

## 本阶段工作

1. 通过必要的只读调查明确原始症状、目标行为、范围与排除项；区分已验证事实与假设。
2. 形成稳定 AC ID 及对应证据要求，明确哪些观察才能证明问题解决；已有 ID 保持含义，新增条件使用新 ID。
3. 记录范围、复杂度、风险与关键未知项；事实不清先调查，提问按上节执行，并记录用户确认与未决项。
4. 记录必要参考、指定技能及产物要求。视觉任务明确文字方案、探索图或实现预览，并核对截图外受影响的同类组件与状态。
5. 提前列出验收证据、环境、授权与缺失前提；缺少运行授权不妨碍独立的只读调查。
6. 按共用澄清规则提交完整需求汇总并核对整体认可，再完成 design 前提判断。需求修订突出变化、确认来源和受影响的设计/AC，引用未变依据，但不省略供用户通读的完整汇总。

本阶段结果写目标、范围、AC、参考与产物、事实/未知项、提问与整体确认来源（或明确免除指令）、复杂度与风险分档，以及 design 前提判断及缺失条件。新索引只登记实际发生内容。

## 交付与停止

新增 `need-<轮次>.md`；骨架字段、落盘顺序、索引同步与停止规则见 [公共流程](workflow.md)。

本阶段完成后推荐 design，传递本轮 need、剩余验证项和负责人；必要关键决定或所需整体确认未齐备时按共用澄清规则受阻。

确认答复和 Cadra ready 的准备请求按 [确认交接](confirmation-handoff.md) 收敛；本阶段只交付 need，不代做 design。
