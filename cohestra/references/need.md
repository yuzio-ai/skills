# need

通过 $cohestra need 调用；与 [公共流程](workflow.md) 一起执行。

## 调用

```text
$cohestra need
需求：<目标、范围、约束和参考>
```

## 输入与职责

输入为原始需求及参考材料，或已有任务目录/handoff。首次任务先核对没有同目标任务，才建立任务目录；需求修订复用原目录。业务文件只读，允许写需求交付与任务索引。

## 澄清提问

方向定错时后续阶段的产出都是无用功，因此提问是本阶段的主要动作，不是附属步骤。先把用户说出的方案与真正要解决的问题分开，再补齐缺口。

1. 先只读调查，再提问。能从仓库、现状、日志、接口文档或截图中确认的，不拿去问用户；只问用户才知道的事——真实目标、优先级、范围边界、验收口径。
2. 一次问成组，不逐条来回。每个问题给候选选项、说明影响，并给出推荐项及依据，让用户选择或修正，而不是开放式发散。
3. 优先追问四类问题：
   - 目标：解决谁的什么问题？现在没有它时怎么做？做成什么样算成功？
   - 分解：这是否属于更大目标的一部分？本次做到哪一步为止？
   - 边界：明确不做什么？哪些既有行为必须保持不变？
   - 验收：出现什么现象才算完成？由谁判定、在哪里验证？
4. 识别被当成需求的方案。用户给出的常是实现手段；先还原成目标再确认，避免把方案直接写进 AC。
5. 确认来源分开记录：哪条来自用户明确回答，哪条是本轮假设。假设必须标出，不能写成已确认决定。
6. 用户不回答或明确「就这些」时停止追问，按已确认内容加明确标注的假设继续，并把未决项写进交付物；不空转等待，也不把假设当已决。
7. 提问轮次由需求不确定性决定，不设固定轮数门槛。目标、范围与验收已明确到可以设计方案，即完成 design 前提判断；未明确时继续提问或列明缺口。

## 本阶段工作

1. 通过必要的只读调查明确原始症状、目标行为、范围与排除项；区分已验证事实与假设。
2. 形成稳定 AC ID 及对应证据要求，明确哪些观察才能证明问题解决；已有 ID 保持含义，新增条件使用新 ID。
3. 记录范围、复杂度、风险与关键未知项；事实不清先调查，提问按上节执行，并记录用户确认与未决项。
4. 记录必要参考、指定技能及产物要求。视觉任务明确文字方案、探索图或实现预览，并核对截图外受影响的同类组件与状态。
5. 提前列出验收证据、环境、授权与缺失前提；缺少运行授权不妨碍独立的只读调查。
6. 完成 design 前提判断。需求修订只写变化、确认来源和受影响的设计/AC，继续引用未变内容。

本阶段结果写目标、范围、AC、参考与产物、事实/未知项、提问与确认来源、复杂度与风险分档，以及 design 前提判断及缺失条件。新索引只登记实际发生内容。
