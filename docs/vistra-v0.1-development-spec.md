# Vistra v0.1 开发 Spec

日期：2026-10-17，Asia/Shanghai。

状态：0.1.2 工作区规格，正式报告与跨 Skill 产物契约 1，profile 格式 2。本轮不安装或发布。当前检查见 [提交前验证](../tests/workspace-review-validation.md)；[0.1.1 精简验证](../tests/vistra-simplification-validation.md) 保留当时边界；[首版记录](../tests/vistra-release-validation.md) 保留历史结果，旧 HTML 路径验证不代表当前静态图片流程通过。

2026-10-21 范围收敛：只生成或编辑静态图片，保留四模式和三领域；移除 Vistra Tools，不制作 HTML、交互原型、审阅网站或运行验证。历史实验与运行记录保留为当时证据，不代表当前执行能力。

目标仓库：`yuzio-ai/skills`。Skill 名称：**Vistra**。标识与包目录：`vistra`。中文定位：**视觉设计评审与探索**。

本规格整合已确认的调用契约、三个设计领域、Taste 定制策略、项目适配、产物模板和 Skill 协作方式。它替代旧 `design-review` 草案中与这些决定冲突的内容。后续实现以本规格和当次用户明确授权为依据；文中的开发步骤不构成本轮实现、迁移或发布授权。

## 1 产品目标与范围

Vistra 依据项目规范和可核实的证据，评审视觉设计、探索方向、比较候选，并形成交接。它统一工作方法与交付契约，保留不同产品的品牌、内容和交互规则。

能力由两个维度组成：

| 维度 | 可选项 | 回答的问题 |
|---|---|---|
| 模式 | `review`、`explore`、`compare`、`handoff` | 本轮做什么 |
| 设计领域 | `mobile`、`desktop`、`brand` | 本轮设计什么 |

四种模式可以独立使用，也可以按明确请求组合。三个领域共享项目依据与品牌决定，按任务需要加载。它们属于一个 Skill，不分别安装。

### 1.1 第一版包括

- 移动端、桌面端和品牌视觉的专项评审、受约束探索、比较与交接。
- 自然语言路由、明确模式调用和组合调用。
- 用户级、项目级 UI/UX 规范与相关 Skill 的协作。
- Vistra 自有的 Taste 定制方法、证据规则与产物模板。
- `.yuzio/vistra` 项目资料目录及与现有 Skill 的引用协议。
- 包结构检查、行为验收场景和实际调用验证要求。

### 1.2 第一版边界

生产代码修改、自动修复、共享规范发布、任务调度、正式工程验收、提交与发布由相应流程承接。Vistra 可以提出规范、Token 或组件变更，但不能把提案写成已批准事实。

第一版不提供自有图像服务、浏览器引擎、模拟器控制器、配套执行器、安装器或长期运行进程。视觉交付为静态图片，直接使用宿主实际可用且已获授权的图像生成或编辑工具；不编写或运行 HTML、原生原型、交互查看器或截图脚本。工具缺失时说明图像交付缺口，不能退回代码制作。

### 1.3 已确定的结构选择

| 决定 | v0.1 要求 |
|---|---|
| 名称 | 使用 `Vistra` / `vistra` |
| 组织方式 | 四模式乘以三个设计领域 |
| 平台处理 | 通用方法按移动端、桌面端组织；具体系统与容器约束由项目提供 |
| 品牌视觉 | 独立支持 Logo、字标、配色、字体和相关视觉系统 |
| 宿主适配 | 不提供 `agents/openai.yaml` 或其他宿主专属入口文件 |
| Taste | 作为开发来源，定制内容由 Vistra 维护，不要求运行时安装或加载 Taste |
| 项目存储 | 默认使用 `.yuzio/vistra` |
| 其他 Skill | 项目资料统一使用 `.yuzio/<skill>`；各 Skill 管理自身容器 |

## 2 调用与路由

### 2.1 显式调用

以下为拟议的对话调用方式，不是终端命令。自然语言明确时无需用户手填全部字段。

```text
$vistra review
对象：当前工作台
范围：信息层级与主要动作
参考：截图、页面路径或规范入口

$vistra explore
对象：移动端设置页
目标：探索三种布局
冻结：现有字段、导航和品牌配色

$vistra compare
候选：A 与 B 的准确产物引用
优先考虑：阅读效率、品牌一致性

$vistra handoff
采用：B 的指定版本
交付：布局、组件、Token 和状态策略
```

同一任务的有效范围、决定和授权持续生效。普通跟进不要求重新确认已确定事项。无法定位当前对象或存在多个可能版本时，只澄清影响执行的缺失项。

### 2.2 自然语言路由

| 请求 | 路由 |
|---|---|
| 看看这个页面、检查哪里有问题 | `review` |
| 给几种视觉方向、重新探索布局 | `explore` |
| 两版哪个好、与当前版比较 | `compare` |
| 就用 B、整理给开发 | 记录对 B 的选择并进入 `handoff` |
| 先找问题，再给两版方案 | `review + explore` |
| 优化一下，且已有明确对象 | 先按 `review` 给诊断和建议；跨入生成或实现前澄清仍不明确的意图 |
| 只有 Skill 名称，没有目标且上下文无法补足 | 询问对象或目标，不扫描所有项目 |
| 讨论 Vistra 的规则、能力或设计 | 保持讨论，不执行视觉任务、不初始化项目资料目录 |
| 直接改代码、提交或发布 | 识别为相应工程请求，由对应流程承接 |

明确限制约束执行，例如“只看截图”“不要出图”“只调整配色”。显式模式与正文发生实质冲突时，先澄清冲突；明确的多动作请求可直接识别为组合。

### 2.3 领域与使用场景

| 请求 | 领域与依据 |
|---|---|
| 探索三种 Logo | `brand`，范围限于 Logo |
| 沿用现有品牌调整移动端首页 | `mobile`，读取已有品牌规范，不自动重做品牌 |
| 比较两套配色在工作台中的效果 | `brand + desktop` |
| 建立品牌方向并展示移动端、桌面端应用 | `brand + mobile + desktop`，共享候选身份与预算 |

界面任务还需识别实际视口、输入方式、界面用途和容器。营销、内容与产品工具的目标分别判断。手机、平板、浏览器和应用窗口不能仅凭操作系统名称决定布局方法。

平台尚未确定时可以探索内容区与视觉方向。会影响设计的返回入口、窗口外壳、弹层和安全区等约束保持待决；交接前按目标项目补齐。公共包不另建 iOS、Android、macOS 的规则分支。

## 3 四种模式契约

### 3.1 review

**输入**：可定位的评审对象、约定范围、至少一种可检查材料。项目规范从有效入口读取；已有截图、概念图、源码和交互记录分别分类。

**执行**：

1. 核对材料对应的对象、版本与状态。
2. 按证据能力检查内容事实、范围、交互结构、信息层级、一致性和局部表现。
3. 将结论分为确定问题、待核实项、可选建议。优先沿用项目严重度定义。
4. 每条发现写清观察、影响、依据、位置和建议；正式报告补稳定 ID、严重度与验证方法。

**输出**：评审范围、按重要性排列的问题、证据限制和必要后续验证。没有发现问题时仍说明实际覆盖范围。

**停止点**：完成约定评审后结束。可以提出具体调整建议；生成替代设计稿属于 `explore`，修改业务实现属于工程流程。

只有源码时执行结构与策略层面的有限评审，不声明视觉效果已验证。只有概念图时评价方向和内容关系，不声明真实交互、字号、触控或无障碍已通过。

### 3.2 explore

**输入**：目标、必要内容、允许变化的范围。既有设计需要可用基线；新设计不要求已有实现截图。品牌任务还需识别新建、延展、局部调整或整体重塑。

**执行**：

1. 建立有来源的必须保留项、允许探索项与未知，说明实际保留与核对方式。
2. 先形成与任务匹配的设计意图和可见决策，再选择工具；各方向说明问题、收益与代价。
3. 使用一致的内容、语言、状态和展示条件表达候选；需变化的条件事先列明。
4. 按视觉目标直接生成或编辑静态图片，实际查看，并分别核对约束符合性与设计质量；不制作可运行原型。
5. 在共享预算内修订，复查受影响项及相邻依赖，分开记录首稿偏差、最终偏差和未验证项。

**输出**：方向说明、约定的视觉产物、冻结项、自检与修订记录、实际预算使用。

**停止点**：交付完成或预算耗尽时结束。自检和简要取舍属于本模式，不自动构成独立评审或完整的 `compare`。

方向应体现本轮允许改变的设计决策。纯配色探索可以比较颜色关系；布局探索不能只换颜色凑出不同方案。产品和阅读任务可比较信息、操作和媒体关系；营销与品牌任务需形成可见的概念、主视觉与构图，居中、分栏或换字体本身不自动成为独立创意。局部任务可用一句意图，不强制完整创意简报或草案阶段。

候选使用相同数据和比较条件。只按请求生成必要尺寸与状态的图片，不制作方向切换器、筛选、详情弹窗或其他交互功能；图片中的操作与反馈仅表达设计意图。

### 3.3 compare

**输入**：至少两个来源可追溯的候选，以及比较目标。当前版本可作为一个候选。

**执行**：

1. 绑定准确产物与版本，核对内容、语言、尺寸、状态和证据类别。
2. 根据用户目标确定比较维度，指出不可直接比较的条件。
3. 使用同一组标准说明候选差异、优势、代价与缺口。
4. 给出推荐，并说明最主要的反对理由或限制。

**输出**：候选清单、可比性说明、关键取舍、推荐与证据缺口。

**停止点**：给出有依据的推荐，或明确无法选优的原因后结束。允许推荐保留当前版本、判定候选均不满足要求，或保持无法选优。不得强行评分、凑出赢家或将推荐记为用户选择。

候选不足时说明缺失项，不捏造候选，也不静默改成另一种模式。数据条件不一致时，只比较仍然成立的维度。

### 3.4 handoff

**输入**：选定方向、选择来源、准确候选版本、目标范围和可读取的项目规范。

**执行**：

1. 核对选择依据及候选是否仍适用。
2. 区分已确定决定、实施建议、新增提案和未决事项。
3. 界面任务映射布局、组件、Token、内容弹性和相关状态。
4. 品牌任务映射素材、颜色、字体、图形语言和使用规则。
5. 列明未实现项、验证方法、所需环境与剩余前提。

**输出**：可追溯的交接说明。关键设计决定和本轮必要候选内容、资源映射齐备时形成完整交接；缺失时只能形成草案，并标明受影响部分。候选代号或区域清单不能替代可核对的设计内容；整页选择明确不自动补足材料。非关键参数可作为提案或待验证项，不要求所有数值已测量，也不重复确认有效选择。明确只请求选择或来源摘要时可完成该限定交付，但不能称完整设计交接。

**停止点**：交接完成后结束。不自动写生产代码、替换项目共享规范或宣布验收通过。

没有选择时可以整理共同约束和已有映射，但不能代选。用户明确说“你选一版并交接”时，可在委托范围内选择，记录为用户授权的 agent 选择，不能写成人工逐项确认。

## 4 组合调用与决定记录

| 组合 | 衔接要求 |
|---|---|
| `review + explore` | 将有依据的问题转为探索目标；范围外问题不自动扩大任务 |
| `explore + compare` | 比较实际生成且可识别的候选；失败或缺失产物不能凑数 |
| `compare + handoff` | 需要有效方向选择或明确的代选委托，才能形成完整交接 |
| 四模式组合 | 按请求顺序执行，逐项检查输入、范围、选择与工具前提 |

组合调用共用上下文、产物引用和预算。前序结果不足时，继续不依赖该缺口的工作；依赖部分保持未开始或未完成，并说明原因。

推荐、方向选择和实现授权分别记录。“就用 B”“按你推荐的 B 交接”属于明确选择；“B 看着不错”不自动授权交接或实现。

选择记录至少包含候选准确引用、选择主体、依据和适用范围。后续明确局部修订可以更新受影响决定，不要求再次批准同一选择。实质偏离原选择且没有新授权时，回到对应设计决定。

多区域或继承预览附简短区域差异：区域、本轮变化、准确来源修订和采用依据；区分本轮调整、沿用已选、暂作参照与仅位置联动。局部采用不自动覆盖相邻参照；已明确采用准确整页组合时，不拆成重复确认。单一对象且无继承歧义时用一句话即可，不增加状态机。

## 5 三个设计领域

### 5.1 mobile

覆盖移动界面、页面关系、触控场景和跨屏一致性。重点检查内容层级、触控可达性、可用空间、输入时的布局、导航与浮层关系、文本扩张和媒体表现。

移动端通用视觉语言可以跨系统复用。具体系统控件、返回方式、安全区和容器语义按项目实际要求处理。已有原生组件不因通用审美偏好被替换。

界面评估默认使用原始页面，不增加设备外框、透视或手持场景。用户要求展示包装时可以采用，并与页面评审证据区分。

### 5.2 desktop

覆盖桌面应用、Web 产品、工作台、营销与内容页面。按界面用途选择方法：

| 用途 | 重点 |
|---|---|
| 产品、工作台、编辑器、工具 | 操作效率、信息密度、状态、表格表单、选择与焦点 |
| 营销与品牌页面 | 内容论证、视觉方向、品牌表达、首屏与长页节奏 |
| 内容与编辑型页面 | 阅读顺序、排版、媒介关系和导航 |
| 紧凑面板、设置或辅助窗口 | 有限空间中的任务边界与主要操作 |

鼠标键盘、窗口变化、焦点和多区域关系属于共同检查内容。浏览器、原生应用和混合容器的差异由项目补充，不强制采用同一三栏结构或同一视觉皮肤。

需要表达窗口关系时可保留必要标题栏与工具栏。它们属于任务相关外壳，不等同于装饰性的设备展示。

营销首屏先从真实产品意义形成主视觉与阅读路径，按概念选择纯排版、图像或混合表达。克制气质不自行解释为禁止图像或固定大留白；真实项目明确限制仍按范围保留。产品工具的结构探索不强加营销表达，代表期间或单轮样例也不证明其他粒度、缺失与错误分支通过。

### 5.3 brand

覆盖 Logo、字标、配色、字体组合、图形语言、图像风格及应用规则。任务范围可以是单项，也可以是完整视觉系统。

先识别任务属于新建、延展、局部调整还是整体重塑。已有品牌元素按请求范围保留；缺少附件不代表没有既有品牌。品牌定位和目标受众优先来自用户与项目，推导内容应标为设计假设。

| 内容 | 交接要求 |
|---|---|
| Logo 与字标 | 选定来源、版本、变体、使用意图，以及尚需制作或核验的母版 |
| 配色 | 明确颜色值、色彩空间、用途与组合关系；可读性结论须有实际依据 |
| 字体 | 可核实的字体名称、字重、来源、可用性与必要回退；未确定项保留为提案 |
| 图形与图像语言 | 构图、形状、图标、摄影或插画的可复用规则与样例 |
| 应用规则 | 本轮涉及的载体、场景、允许变化与保持一致的部分 |

生成的 Logo 概念图不能冒充可编辑矢量母版；图中字体外观不能证明实际字体名称或规格；示例应用图不能证明产品实现完成。

品牌探索可以使用概念板、色板、字体样张和应用示例。只请求 Logo 时，不默认扩成完整品牌套件。

概念需在主画面及相关载体上成立；参数表和旁注不能替代视觉表现。已有 Logo/Signature 以准确原稿作为图像参考或编辑输入，同时检查图中的比例、净空、背景和组合关系。无法精确保留时记录缺口，不把生成图当作合格母版，不为补齐精度追加代码制作。

### 5.4 跨领域一致性

已有品牌规范是界面任务的输入，不因读取规范就启动品牌重设计。尚未选定的品牌方向，其移动端和桌面端示例必须绑定具体候选。

选定后，两端引用同一份有效品牌依据。新增应用方式仍需区分沿用规则、设计提案和已确认决定，不能在各端独立发明互相冲突的颜色或字体系统。

## 6 公共执行流程与预算

一次执行遵循：确定目标与范围 → 解析项目依据 → 选择模式与领域 → 建立约束依据和预算 → 按任务形成意图与选择表达 → 产出、约束核对与设计判断 → 交付结果与缺口。评审、比较和局部任务按范围简化，不增加固定流水线。

### 6.1 冻结与探索

冻结项包括本轮未授权改变的功能、内容字段、领域含义、导航、权限、品牌规则和素材身份。每项应有任务或规范来源。

探索项只覆盖请求范围，例如布局、分组、层级、留白、媒介比例，或明确请求的 Logo、配色与字体变化。信息架构、业务语义和交互流程的扩大需要明确设计任务支持。

关键约束用“来源及要求 → 实际保留方式 → 各候选满足/违反/未验证及证据条件”核对。共用数据、组件和素材可合并记录，不强制全量表单。文案、数据与原资产优先直接引用；实际使用仍需核对，文件相同不证明未被拉伸、错误裁切或重组。字段存在不证明状态、单位、导航目标和缺失值含义未变。报告、图像生成或编辑提示词和参考素材应保持同一约束，修订复查受影响项。

违反必须保留项的候选可保存为过程记录，不能作为满足约束的方案推荐；关键未知限定建议，不自动等同违反或通过。选择不自动豁免事实与必要条件，也不要求用户重复确认有效的视觉取舍。

### 6.2 预算

- 独立的多方向探索默认三个方向，最多一轮针对性修订。明确要求单方案时按单方案执行。
- 当前任务要求和调用方已确定的数量、范围与预算优先。Cohestra 已确定一套代表图时，不自动扩成三套。
- 方向数量与图片数量分别记录。执行前根据目标确定代表图与必要状态图，避免按领域或页面无条件相乘。
- 多模式、多领域共用一份本轮预算；进入下一个模式不能重置预算。
- 一轮修订是对已识别问题的一次有界修订，不是重复执行整套探索。扩大轮次或产物范围须有任务依据。
- 到达预算仍有问题时交付已有成果和缺口，不通过无限重试追求满分。

### 6.3 表达方式与自检

概念先于工具。新方向直接生成静态图片；局部调整向图像编辑工具提供现有图片、准确内容和原素材，限定变化区域。按请求提供必要的多尺寸或状态图，不制作 HTML、交互原型或审阅网站。纯排版也可形成强构图，不默认只输出文字与细线。

表达选择记录要判断的目标和理由。生成工具未准确执行几何修改时，在剩余预算内针对性修订，仍不满足则保留精度缺口，不改做代码原型。密度任务同时观察局部关系与父区域占用，图中像素不等于实际平台布局单位；产物完成与核心目标是否达到分别说明。

重新生成整页不能证明非目标区域像素不变。生成后必须实际查看产物，检查事实、内容、范围、交互结构、信息层级和局部精度。关键文字、图标或数据失真必须记录并在预算内纠正。

示例数据应标明用途。不能以隐藏错误、删除字段或缩小文字来维持漂亮截图。生成工具自身限制与设计问题分别记录。

构思、草案与完整制作共用预算。多方向的比较价值来自目标所需的设计差异，数量、可交互或技术检查通过不单独证明视觉质量。实际查看主视觉、注意力顺序、字体、媒介与内容关系，允许全部候选偏弱、目标未达到或保留当前；审美结论与约束违反分别记录，不虚构用户偏好或效果测量。

多方向或多载体放入组合图片时核对缩放、裁切、可读性和标注；分别查看实际交付图片，不用组合缩略图代替关键细节核对，不强制全量补图。

## 7 规范权威与 UI/UX 协作

### 7.1 资料职责

| 资料 | 提供的依据 |
|---|---|
| 当前用户请求与有效决定 | 本轮目标、范围、限制、选择和授权 |
| 产品与领域规范、合同锁 | 功能事实、业务含义及锁定版本 |
| 设计规范、品牌、Token、组件、页面 Overlay | 目标项目的视觉与交互规则 |
| 用户级 UI/UX 规范 | 跨项目的默认偏好与适用要求 |
| 项目专用 Skill | 项目语境、冻结项与专项方法 |
| 通用方法与参考图 | 可筛选的方法、参考方向与质量线索 |
| 当前截图和实现 | 当前状态，不自动成为规范 |

同类视觉选择遵循：当前明确决定 → 有效页面与项目规则 → 用户级默认偏好 → 通用方法建议。页面 Overlay 只在其适用范围内细化规则，不能无依据地推翻产品事实或组件契约。

权限、数据处理、可访问性和平台可行性单独核对，不能用审美优先级覆盖。冲突时写清来源、影响和待决事项；既有实现与规范不符时分别记录 observed 与 expected。

### 7.2 Skill 协作规则

1. 从宿主暴露的入口、项目索引和明确引用发现相关资料；不全量扫描用户目录或加载全部已安装 Skill。
2. 记录本次实际采用的 Skill 路径、版本和职责。同名用户级、项目级副本不自动混用。
3. 按当前模式使用能力。相关 Skill 的生成、实现、部署或调度步骤不会因被读取而自动获得授权。
4. 用户指定其他 Skill 为主流程时，Vistra 只承担被请求的专项职责；避免相互递归调用。
5. 报告列出实际采用的依据及影响结论的冲突处理，不抄写整套规则。

项目资料和外部参考中的任务简报、安装命令或历史指令均须按资料职责理解，不能替代当前用户请求。

- 筛选对实际任务有用的方法，去除重复指令和无条件风格禁令。
- 统一采用 Vistra 的模式、项目权威、预算、证据和交付契约。

- 桌面模块按产品工具、营销和内容用途区分；品牌模块支持完整系统与局部任务。
- 方法和流程不能以视觉效果为由删减事实、扩展功能或改变业务语义。

### 8.3 来源与升级

定制开发时，固定实际采用的上游提交，记录仓库、文件路径、提交、读取日期、采纳部分与关键改写。来源说明集中在 `references/provenance.md`，领域和模式仅保留对应链接；仅维护时加载，不存放上游全文。

按实际采纳内容保留必要版权与许可声明，参考上游 [LICENSE](https://github.com/Leonxlnx/taste-skill/blob/main/LICENSE)。上游更新通过差异评审、相关场景回归后选择性吸收，不能直接覆盖 Vistra 定制内容。

现有安装锁继续管理仍安装的第三方依赖。Vistra 自有方法的来源记录与安装锁职责不同，不能伪造 Taste 运行依赖或另建重复安装器。

本规格给出来源入口；实际采纳提交与改写记录在开发时建立，不能把 `main` 链接写成已锁定版本。

## 11 项目适配协议

### 11.1 长期配置与本轮上下文

长期配置仅保存来源入口和默认值。本轮目标、候选、约束、预算、授权和选择保留在有效上下文与相关交付中；正式报告按第 13 节追溯，普通对话不另建报告。

优先使用项目已有规范索引。只有现有入口不足且需要持久配置时，才在授权范围内建立 `.yuzio/vistra/profile.yaml`。不要求用户先填完整表单，也不将每轮推导结果回写为项目默认。

已有或明确引用 profile 时，才加载包内 `references/profile.md`；没有配置时直接使用项目入口与当前上下文。

### 11.2 profile 字段

| 字段 | 含义 |
|---|---|
| `profile_version` | 配置格式版本，0.1.2 使用 `2`；其他版本不按 v2 解释 |
| `project` | 项目稳定名称或标识 |
| `sources` | 按资料角色组织的引用列表 |
| `defaults` | 语言、外观、输出目录和预算等可覆盖默认值 |

`sources` 支持 `canonical`、`design`、`brand`、`tokens`、`components`、`page_overlay`、`adapter`、`policies`、`assets`、`mock_data`。角色说明资料用途，不能仅靠把外部文档填入 `canonical` 就赋予项目权威。

```yaml
profile_version: 2
project: example-product

sources:
  canonical:
    - docs/PRODUCT.md
  design:
    - docs/DESIGN.md
  brand:
    - docs/BRAND.md
  policies:
    - docs/DATA_POLICY.md
  adapter:
    - .agents/skills/example-ui/SKILL.md

defaults:
  locale: zh-Hans
  appearance: light
  output_directory: null
  budget:
    variants: 3
    refinement_rounds: 1
```

`sources` 的值为引用列表；引用可以是明确文件、链接或宿主提供的 Skill 标识，实际使用前解析到可读取内容。Skill 与其他资料一样按本轮相关性读取，不另建 imports、作用域或条件加载配置。具体对象、领域与用途由本次任务及有效上下文确定，不配置 `domains`、`targets` 或 `imports`，不做多层继承。不支持的字段保留并说明未采用，影响本轮约束时从项目规范或明确输入核实，不自动迁移。

用户级规范从宿主已提供的有效入口或明确引用读取；不预设新的用户级配置目录。未知格式版本应报告无法可靠解释的部分，不按旧版强行解析。

### 11.3 解析规则

1. 固定目标项目根目录，不能因切换目录或技能安装位置而改变目标。
2. 读取适用项目入口，再读取明确 profile 与本轮相关来源。
3. 只读取本轮相关来源并去重；实际内容按第 7 节判断。
4. 默认值逐字段按当前明确要求 → 调用方已确定值 → profile 默认 → Vistra 默认解析；显式零值不视为缺失，无效预算报告缺口，不用默认值覆盖项目约束。
5. 记录已读取、缺失、冲突和仍需确认的材料；只阻塞依赖缺口的交付。

profile 中相对路径统一相对于目标项目根目录。技能内部引用相对于实际加载的技能目录。跨仓库来源使用明确入口，不猜测用户机器上的固定路径。

空值代表未知或未设置，空列表代表未声明来源；二者都不证明没有约束、已经授权或已经通过检查。profile 不保存运行授权布尔值、选定候选、当前截图或旧执行状态。

本轮有效上下文按实际需要覆盖：目标与范围、请求模式和领域、来源及版本、基线与候选、显示条件、冻结与探索项、预算、授权依据、选择记录、输出位置和关键缺口。能安全读取或推导的项由 agent 整理；未变内容可准确引用上轮，不能把表单负担转给用户。

## 12 证据模型与结果语义

### 12.1 证据类别

运行截图、交互与无障碍结果仅可引用用户或上游已有证据，标明主体与来源，不由 Vistra 启动运行。保留这些类别用于解释历史材料；本轮新视觉产物为静态图片。

| 类别 | 可以支持 | 不能单独支持 |
|---|---|---|
| `specification` | 预期规则、范围与约束 | 当前实现已遵守 |
| `concept-image` | 视觉方向、内容关系、概念可读性 | 精确字体指标、真实交互、正式无障碍结论 |
| `runtime-capture` | 指定候选、尺寸和状态的实际显示 | 其他尺寸、状态或辅助技术的表现 |
| `source-inspection` | 组件、Token、代码结构与布局策略 | 实际渲染必然正确 |
| `runtime-interaction` | 已执行路径上的行为结果 | 未执行路径没有问题 |
| `accessibility-check` | 实际检查项目的结果 | 全应用无障碍认证 |
| `asset-inspection` | 实际素材的格式、颜色值、字体信息、变体等已核验属性 | 未检查的编辑能力、使用条件或所有应用效果 |

证据记录至少保留类别、准确来源、对应对象或候选、观察结果与限制。尺寸、语言、外观、状态、环境、构建和捕获时间按实际可获得信息填写；概念图不能补造运行设备、系统或构建信息。

候选比较前核对输入条件。概念图与运行截图可以讨论设计关系，但不能将证据类别差异当作实现质量改善的证明。

### 12.2 问题记录

正式报告中的问题包含稳定 ID、性质、严重度、观察、影响、依据、位置、建议和验证方法；普通评审按第 13 节精简交付。复审沿用原 ID 与来源，区分原有问题、新回归和未核实风险。

沿用项目严重度；没有定义时使用：

- **Blocker**：事实、权限、关键内容、主要操作路径或必要结构受到严重破坏。
- **Major**：重要层级、可读性、主要动作、一致性或适配存在明显问题。
- **Minor**：局部节奏、对齐或视觉细节可改进，不妨碍当前方向讨论。

审美偏好不能抵消 Blocker。未知项保持未知，不凭空判为通过或失败。

### 12.3 四个独立结果维度

| 维度 | 必须说明 |
|---|---|
| 交付完成度 | `completed`、`partial` 或 `blocked`，以及未完成的请求部分 |
| 设计判断 | 发现、推荐、讨论可继续的范围与剩余不确定性 |
| 方向选择 | 未提供有效选择、用户选择或授权代选；绑定候选及依据 |
| 实现验证 | 实际检查项目、结果、对应证据与尚未执行的部分 |

这些字段描述本次专项结果，不是新任务状态机。评审发现严重问题仍可能完成评审交付；完整设计交接不代表实现或验收通过。未获得有效选择记录时，不应声称用户从未选择过，应说明本轮尚无法确认。

单项检查区分通过、失败、未运行和环境受阻。组合调用逐模式标明实际执行范围，不能因其中一项完成就将整次交付标为完成。

约束符合性和设计质量在设计判断中分别说明，不新增模式、结果状态或 profile 格式。review/compare 可完成并发现全部候选不合格；explore 实质请求合格方案却只交违规稿时保留交付缺口。作者自检不成为独立评审，首稿偏差不因修订后通过而被抹去。

## 13 产物模板与候选引用

### 13.1 公共报告骨架

普通对话与本机过程记录按模式直接交付，不强制版本、契约、作者关系或四个结果维度；必须给依据并说明影响结论的未知、未完成项和候选歧义。是否正式交付按用途和项目规则确定，不仅看是否落盘。

正式报告、正式交接和跨 Skill 返回使用公共骨架，保持现有完整追溯语义。模板只组织内容，不另定义规则。组合模式共用上下文与证据，逐模式说明范围和缺口。后续轮次只写变化并准确引用上轮；不隐藏关键未知。

```text
标题：<目标对象> · <模式或组合> · <轮次>

身份与输入

本轮有效上下文
```

### 13.2 四种模式的交付内容

交付要求直接维护在对应模式的“交付与停止”，不另设模式模板。

| 模式 | 内容 |
|---|---|
| review | 发现、位置与依据、影响、建议和必要限制；复审沿用问题 ID |
| explore | 候选图片、方向差异、自检、必要预算与缺口；涉及修订时保留首稿和最终偏差 |
| compare | 准确候选、可比范围、推荐理由与主要代价 |
| handoff | 准确选择、采用范围、必要设计说明与资源映射、待决和未验证项 |

品牌交接仅展开本轮相关元素；公共字段语义由 `evidence.md` 统一定义，正式报告骨架见 `assets/report.template.md`。

交接保留选定主视觉的概念、主体尺度、叠压/纵深、材质、准确文案与素材、裁切及适配关系。组件映射不能静默删除主视觉或改成通用栅格；冲突列出损失与待决部分。图片中的操作仅表达意图，真实行为不因方向已选而变为通过。

### 13.3 按需记录语义

| 记录 | 字段 |
|---|---|
| 候选 | 报告内简称、准确产物引用、版本或修订、证据类别、可获得的显示条件 |
| 组件映射 | 界面角色、现有组件或 Token、来源、采用方式、缺口或新增提案 |
| 品牌映射 | 元素或规则、选定来源、用途、已确认参数、待制作或待验证项 |
| 决定 | 决定内容、主体、来源、适用范围、对应候选与覆盖关系 |
| 资源记录 | 实际可观测的图片数量、修订轮次、工具结果及成本信息；未知值不估填 |

`A/B/C` 仅为报告内简称。后续必须引用准确报告与候选版本。可获得文件哈希或稳定版本时用于核对；原路径已变且无法确认候选时，不宣称旧选择仍对应当前内容。

### 13.4 命名与保留

缺少已有约定时，采用 `vistra-review-01.md`、`vistra-explore-01.md`、`vistra-review-explore-02.md` 等名称。视觉产物区分 `concept-B-r01.png` 与 `runtime-baseline-01.png`。扩展名必须与实际文件格式一致。

新轮次保存新产物并引用上轮，不覆盖仍被选择或交接引用的候选。已有稳定素材可以引用原位置；共享报告中优先使用可随项目解析的相对引用，对话提供可打开的准确入口。

对话默认只展示结论、最重要的问题或方向差异、推荐与代价、必要决定以及产物入口。需要正式报告时保存完整依据；不为普通对话额外创建报告。

## 14 现有 Skill 协作协议

### 14.1 职责与数据流

| Skill | 所有权 | 与 Vistra 的关系 |
|---|---|---|
| Cadra | 任务、依赖、队列、Run 与恢复 | 按既有协议调用 Cohestra；不直接把 Vistra 的交付状态当作 Run 控制状态 |
| Cohestra | 工程阶段、任务交付与正式验证 | 在设计阶段调用探索、比较、交接；在审查或验证阶段按证据调用视觉评审 |
| Vistra | 视觉专项方法、发现、候选和交接 | 返回结果和产物引用，不写其他 Skill 的状态 |
| Relatra | 事实采集、目标归并、统计与周期报告 | 在适配后只读视觉产物及有效执行证据，按独立目标汇总 |

这些能力按需组合。独立 Vistra 调用不要求先初始化全部工程流程，Relatra 也不是每次设计结束后的必经步骤。

### 14.2 调用输入

调用方传递可获得的以下内容，具体传输方式沿用宿主，不新建 CLI 或 RPC：

- 目标项目、父任务引用、目标对象和范围。
- 请求模式、顺序、领域与预期交付。
- 当前有效规范、品牌依据、基线和候选引用。
- 冻结项、允许变化项、选择记录与执行限制。
- 本轮预算及可执行动作的授权来源。
- 输出位置；未指定时使用 Vistra 默认目录。

调用方已确定的任务预算与决定优先于 Vistra 默认。上层未授权的运行、图像外发或实现动作不能由子调用自行补齐。

### 14.3 返回结果

Vistra 返回实际包版本、产物契约版本、准确产物入口、请求与实际执行模式、设计领域、逐模式结果、四个结果维度、选择依据、证据限制和必要前提。

调用方核对对象、候选、版本和产物可读性后消费结果。返回缺失、版本无法解释或产物不存在时，不能按成功继续。v0.1 使用可读报告承载这些字段，不预先要求自动解析器。

Vistra 不返回可直接改写上层状态的 `next`、工程 `acceptance` 或任务 `completed` 指令。Cohestra 根据自己的契约形成正式阶段结果；Cadra 只消费 Cohestra 的控制契约。

### 14.4 审查与验收

Vistra 的作者自检不构成独立审查。被工程 `review` 或 `validate` 调用时，应记录实际执行者、证据范围和与候选的关系，不能用设计稿或作者摘要替代所需检查。

“视觉专项报告已交付”“方向已选定”“实现已验证”分别记录。Vistra 不能关闭由其他流程管理的发现，也不能降低其验收要求。

### 14.5 Relatra 接入

Relatra 按目标与证据归并，不把每张图片、每份报告或每个候选计为独立成果。只采纳可观测的执行成本；无 token、时间或费用数据时保持未知。

当前 Relatra 的自动采集与 `.yuzio/vistra` 解析能力必须在后续适配后验证。本规格只定义接入契约，不声称现有版本已自动支持新路径。过渡期使用明确的产物引用与既有证据机制。

### 14.6 项目专用 Skill 迁移

现有项目探索 Skill 的产品规则保留在项目仓库。接入 Vistra 时将上游方法引用逐步替换为 Vistra 定制方法，并在实际授权的项目变更中同步组合策略文档。

旧适配器内部的局部、页面或概念探索分类映射为探索范围，不替代 Vistra 模式。截图按当前状态解释，自检与修订受本轮预算约束。未迁移的组合策略必须显示兼容缺口，不能宣称已经无依赖接入。

项目覆盖层保留产品、平台和品牌约束；Vistra 负责静态图片的模式与证据方法。仍要求旧执行器、HTML 原型、交互验证或固定整页输出的方法须单独核对冲突，不混成有效规则。代码与运行行为由工程流程承接，不以静态图冒充完成；修改适配器与组合策略仍需项目变更授权。

## 15 工具缺口与数据边界

| 情况 | 可继续的工作 | 必须保留的限制 |
|---|---|---|
| 没有图像工具或相关授权 | 文字方向、布局说明、生成简报 | 承诺的图像交付未完成 |
| 请求包含运行或交互验证 | 检查已有图片、材料与源码，列出工程待验证项 | 不启动运行环境，不将静态画面写成行为通过 |
| 规范不可读 | 基于实际观察给有限意见 | 不声称符合缺失规范 |
| 候选数量不足或不可定位 | 整理比较前提与缺失项 | 不完成选优，不伪造候选 |
| 没有有效方向选择 | 整理共同约束与交接草案 | 不宣布完整交接或人工确认 |
| 无法保存要求的产物 | 对话中提供可交付内容与缺口 | 不编造路径或持久交付成功 |

继承项目数据政策，使用批准的示例或脱敏资料。需要外部处理时核对实际提交内容与授权，不能仅遮挡姓名就认定敏感图片、编号或附件已脱敏。

外部参考用于理解方法与方向，不冒充本项目素材。示例数据不能变成真实产品能力、评价、成绩或业务结论。公共 Skill 包和测试夹具只包含通用方法与脱敏示例。

| V28 | 旧截图与当前规范冲突 | 分别记录 observed 与 expected |
| V29 | profile 带旧候选或授权数据 | 不将其作为本轮选择或授权依据 |
| V30 | 首次落盘与只读请求 | 按实际写入需要建自己的目录；只读限制下不初始化 |
| V31 | 新轮次与旧候选 | 保存新产物，旧选择仍可准确定位 |
| V32 | Cohestra 调用 | 返回专项结果，不写工程任务状态或宣布正式验收 |
| V33 | Cadra 衔接 | 保持通过 Cohestra 控制契约推进，不消费 Vistra 字段作队列状态 |
| V34 | Relatra 衔接 | 按独立目标与实际证据归并，不将图片数当成果数 |
| V35 | 已有 `.yuzio/cohestra`、`.yuzio/cadra`，执行 Vistra | 只引用资料，不初始化或改写其他 Skill 的容器 |
| V36 | 未安装 Taste | Vistra 定制方法可执行；所缺图像工具单独报告 |

### 16.1 静态与结构检查

检查名称与描述、引用可达性、示例格式、模板字段一致性、来源说明、许可证、公共包是否包含私有资料，以及是否存在已排除的宿主专属文件或操作系统分支。

这些检查只证明结构与文本契约一致，不能证明 agent 正确路由或生成质量合格。

### 16.2 实际调用验证

实际调用验证目标至少覆盖四种模式和三个领域，并包含桌面产品与营销页面的区分、一次跨领域品牌应用、组合调用和关键降级场景。一个场景可以覆盖多个维度，但应给出实际覆盖矩阵。按 2026-10-21 的发布决定，0.1.0 先作为项目试用版发布；静态图片范围收敛后的 S01–S06 留待项目试用，不以历史原型结果替代，也不作为本次发布的阻塞条件。

记录实际输入、环境与权限、采用版本、产物、成功与失败、未知项及可观测成本。执行者与作者关系如实记录；独立执行与同一作者自检分别报告。额外运行、外发和独立执行需要符合当次任务授权。

### 16.3 首版完成条件

- 四模式、三领域、适配协议和模板已实现且结构检查通过。
- 代表任务的实际行为有可复核证据；要求覆盖的场景未运行时保持待验证。
- 运行不依赖 Taste 安装，且来源与定制记录可追溯。
- `.yuzio/vistra` 的写入边界、候选保留和交接引用已验证。
- 与其他 Skill 的协议边界得到验证；尚未完成的自动化接入明确列出。
- 未完成项不被“包校验通过”或“图片已生成”掩盖。

## 17 后续开发顺序

以下顺序仅在用户另行启动实现后执行。

1. 固定 Taste 采纳基线，完成三个领域的规则筛选与定制设计。
2. 实现轻量入口、四模式、三领域、项目适配与证据规则。
3. 完成公共报告、模式正文、profile 示例及 `.yuzio/vistra` 产物约定。
4. 完成静态检查与行为场景，使用授权的代表任务执行真实验证。
5. 在明确授权的项目中接入已有 UI/UX 规范和专用 Skill，验证规则未被通用方法改写。
6. 核对四个 Skill 的 `.yuzio/<skill>` 目录、跨 Skill 引用及采集路径；尚未实现的 Vistra 自动采集单独适配和验证。
7. 根据真实重复工作添加必要的窄范围脚本，不预先重写上游完整工具链。

实现、验证、迁移与发布分开记录。Spec 完成不代表 Skill 实现完成；Vistra 完成不代表其他 Skill 的自动化接入已验证。提交、推送、发布、运行受限环境和修改业务项目按当次实际授权执行。
