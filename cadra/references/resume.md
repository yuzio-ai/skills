# resume

通过 $cadra resume 调用；与 [公共流程](workflow.md) 一起执行。从持久化状态恢复未完成 Run，接着串行推进。

## 调用

```text
$cadra resume
Run：<run-id；可空>
补充：<本次人工决定、补充输入或权限，可空>
```

run-id 缺省时取唯一的未完成 Run；存在多个候选时列出并请用户指定，不凭创建时间或“最新”猜测。

## 职责与工作

先读取指定 Run 的状态；已 completed 或 stopped 且已出队收尾时只报告结束事实，指向 report。需恢复其 blocked/failed 时给出 run 的显式恢复调用，不改变旧 Run。推进前确认目标仍可安全写入且满足 Cohestra 初始化前提（[公共流程](workflow.md) 第 6.1 节，Git 工作区）、本次加载的 Cohestra 可用且支持所需契约，同时没有其他未完成 Run；否则报告并停止。仅做收尾、不调用阶段时不因 Cohestra 缺失或目标非 Git 而拒绝队列清理；第 2 条的入队／出队部分写入补齐同样不调用阶段，可以先独立补齐并如实报告结果，但要继续推进仍需满足上述前提。running 结果仍必须可核实，否则按第 9 条收尾规则记 failed。

1. **从持久化状态恢复**：读取 Run 文件、其 checkpoint、`queue/order.md` 与相关 Task 文件，重建执行顺序与进度；同时核对入队与出队的写入完成度（Run 记录的 `enq-`/`deq-` 编号与实际 Task 状态、队列行是否一致），不依赖聊天记录，不新建 Run。
2. **先补齐部分写入，再推进**：入队或出队中断留下部分写入时，按 [公共流程](workflow.md) 第 4 节第 7–9 条**先判阶段再补齐**——读 Run 中该 Task 有无结果快照：无结果快照按**入队阶段**补齐（`enq-<run-id>-<NN>` 与定义快照存在、且与实际 Task 定义 slug／cohestra_task／requirement／flow 一致时判为同一次入队：Task 仍为入队前状态且本 Run 无该 Task 的阶段调用记录则补 Task 与队列行，已是 `queued`/`running` 而队列缺行则只补队列行）；有结果快照按**出队阶段**补齐（以 Run 快照为唯一依据，Task 状态与快照不符时补 Task 终态或 `skipped` 回退 `ready`，该行结论列为空时补回写）。**不得只凭 Task 状态字面值判断**：`blocked`／`failed` 既可能是恢复任务入队前的原状态，也可能是本 Run 的终态，混判会把终态任务误报为矛盾。
   **旧记录例外**：v0.4 及更早的 Run 与队列行没有 `enq-`／`deq-` 编号，**编号缺失不构成停止条件**——定位一律以消费 run-id + slug 为基准键（`enq-` 编号只在存在时用于区分同一键下的多行），核对用 Run checkpoint 的「入队定义快照」与结果快照，回写落在该行自身既有的结论列（旧表块写它本来就有的「出队结论与时间」单元格）。这条路径必须有可达的收尾：不得因为「没有新版编号」就停在停止分支，把旧 Run 永久留在未完成状态。
   补齐范围仅限「尚未写入的步骤」：不重复追加行、不重写已有结论、不动其他 Run 的行。以下情形停止并报告，不补写、不猜测：同一 run-id + slug 匹配到多行且无法用 `enq-` 编号区分、定义快照与实际 Task 不一致、入队阶段出现「入队前状态却已有阶段调用记录」、Task 状态与 Run 快照互不相容、Run 快照与队列结论互相矛盾。**部分写入未补齐前不调用任何阶段**；该情形不按记录矛盾处理，也不因补齐需求放宽 `add` 的归属拒绝。
3. **保留终态**：completed、blocked、failed 的 Task 不重跑、不因原因解除或重试请求改回 queued，按本 Run 已保存结果计入；需要重试时先结束或收尾本 Run，再通过 run 显式恢复进入新 Run。
4. **不重复已完成 Cohestra 阶段**：以 checkpoint 的最后交付阶段、结果与轮次为准，回读 `cohestra_task` 的结构化状态核对实际进度与索引完整性；两者一致且同步已确认才按 `next` 继续。`next` 指回本阶段表示下一轮，不跳过，不凭文件修改时间或文件编号推断。
5. **重新核对可继续的状态**：
   - `running` 且 checkpoint 未闭合（中断点）：按第 6 节「本次结果核对」比较拟调用阶段、调用前阶段/轮次、本次声明的 execution_mode 与当前契约；先确认完整 README 与本轮 handoff 一致、同步成功且执行模式相符，才补记 checkpoint 并按 `next` 继续。读取到旧结果、缺失调用前记录、存在 `index sync failed` 且尚未核实恢复，或无法判定时停止该 Task，按 run 的失败口径报告；不自动重跑已落盘阶段，不假定成功。
   - queued：先重核依赖落盘状态——任一依赖非 `completed` 时按 [公共流程](workflow.md) 第 4 节第 4 条记 `blocked`（依赖未满足）出队，不沿用入队时保存的待调用动作；依赖满足时使用本 Run 为该 Task 保存的待调用动作及定义快照；首次启动仍须满足第 6.1 节无交付、无调用条件，修订重启项按第 6.3 节核对 `rev-<N>`、原终态与重启起点。恢复或修订重启授权尚未消费时沿用原记录，已消费但未闭合时先核对本次结果，不能再次绕过旧 next 调用。
   - running 且 checkpoint 已闭合：按核实后的本次结构化状态映射继续或记终态，不重新调用已结束阶段。记录矛盾时停止并报告，不偷偷修改 Task 定义。
6. 续跑沿用原 Run 的 `execution_mode: unattended` 与各 Task 的 execution policy，不切换模式（[公共流程](workflow.md) 第 7 节）。
7. 恢复后的串行执行、终态映射、三项上限与无进展判据、`stop_queue_on_failure` 及落盘规则与 [run](run.md) 相同；checkpoint 中逐阶段重试预算、已消费的整改轮数与调用总数一律沿用不清零，按调用标识去重，回读或补闭合同一交付不重复计数；缺记录或矛盾时停止，不补造预算。`resume` 不以任何方式重置预算或整改轮，也不因补齐部分写入而返还额度。
8. 全部 Task 到达终态后结束本 Run；closed Run 不因后来 Task 被新 Run 恢复而重开。
9. **放弃续跑（Run 收尾）**：用户明确不再续跑时，按 [公共流程](workflow.md) 第 3 节先核对 running checkpoint、记录实际结论或无法确认的 failed，再将 queued Task 出队回 ready。保存逐 Task 结果、队列出队结论与时间（含 `deq-` 编号）后才标记 stopped/已收尾；未写完的部分按第 2 条补齐口径处理，不改 Task 定义，不启动下一阶段。
10. 恢复过程中无法读取必要状态或记录互相矛盾时，如实报告缺口并停止推进，不猜测进度、不覆盖既有记录；第 2 条列出的部分写入情形除外，那是可判定的补齐，不是矛盾。

## 交付与停止

更新 `runs/<run-id>.md` 的 checkpoint 与 Run 状态、`queue/order.md` 与相关 Task 状态；落盘规则见 [公共流程](workflow.md)。

推荐下一步 `report`；派发：`$cadra report`，后附 run-id 及本次补充。
