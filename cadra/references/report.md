# report

读 [公共流程](workflow.md) 与所选 Run；优先使用 Run 中的结果快照与调用记录，仅在解释缺口或异常时按需读取相应规则和证据，不默认通读全部 Cohestra handoff 或原始日志。不重新做 Gate、预算或执行判定，不重跑工程阶段或验收。

选择 Run 后先按下方“逐任务运行过程”运行包内只读工具，取得实际调用与事件顺序；工具失败时报告记录异常与准确路径，不绕过校验生成正常完成结论。

```text
$cadra report
Run：<run-id；可空>
补充：<关注点，可空>
```

未指定时优先唯一未完成 Run；没有未完成 Run 且仅一个 Run 时使用它；其他情况列出候选请用户指定，不凭“最新”猜测。

补充中明确要求补登记已生成报告时，仅按下方保存规则核对并登记指定路径，跳过报告新增，不重新生成正文。

## 收尾自动报告

- run/resume 本次将 Run 收尾为 completed，或所有条目均已终态、结果完整且小组均已 close 的 stopped，并成功落盘回读后，自动复用本页流程一次，显式指定当前 run-id，不重新选择 Run，也不要求用户另行调用。completed 中存在 blocked/failed 项仍生成报告；用户停止和策略停止的闭合 stopped 同样适用。
- running、interrupted、仍有 queued/running/waiting 项或未闭合小组的 stopped，以及记录异常或收尾未确认的 Run 不自动生成报告。resume 入口时已经结束的 Run 保持只读，不补生成或补登记；若收尾后、报告前中断，通过显式 `$cadra report` 加 run-id 补齐。
- 自动报告属于 run/resume 的收尾交付，不新增工程调用或消费阶段预算。先前手动生成的进行中报告不能代替本次收尾报告。手动 report 仍可生成阶段报告、按关注点整理或再次生成报告。

## 内容与保存

- 使用该 Run 的结果快照与调用记录，汇总 completed/blocked/failed/skipped；未结束条目另列进行中，不计为失败或跳过。文首注明 Run 状态。
- 每项写状态、最后交付、候选引用、findings 摘要、acceptance、人工介入与下一步。保留 passed/failed/pending/blocked，只有无证据才 unknown。
- 工程交付终点单列工程完成、整体验收和原生待办。引用冻结决定及最终 review，写清待办、负责人和恢复条件。验收缺省记 unknown，已有结论保留原范围。整批收尾结论单列。
- 恢复/修订说明来源 Run 与定义 revision。无需调用的收尾明确沿用的候选、验收与原模式，不冒称本轮执行。当前 Task/Cohestra 状态只能单列补充，不能替换旧结果。
- 人工介入集中列出待决定、权限/输入缺口、失败、预算耗尽、协议/模式核对失败与无法确认的调用。正常 flow 边界保留截断范围和实际验收结果。
- 仅对 0.12 Run 生成报告；旧协议按 [版本边界](compatibility.md) 停止，不解析或登记。报告另列追加批次、实际角色身份与替换来源、审查方式、覆盖缺口和代码/运行验收边界，引用 Cohestra 证据，不从正文重新决定推进，也不重写旧结果为后续修复结果。
- 报告长度随任务复杂度调整；简单任务紧凑列出必要结果，复杂任务保留逐项交付与证据边界，不复制调用全文或原始日志。
- 按公共流程原子新增 `runs/<run-id>-report-<轮次>.md`，报告轮次至少两位（`01` 起），不覆盖已有报告；含 `-report-` 的文件按报告处理，不参与 Run 扫描。回读后经 [guard report](executor.md) 在 Run 追加报告链接。不得更改原结果。
- 报告生成失败不回滚 Run、不改任务终态或预算。链接登记失败时保留已生成文件，明确其准确路径与未登记状态；同次重试或用户明确要求补登记时，先核对文件属于该 Run 并回读，不重新生成。重读最新 Run，已存在该路径链接则不重复追加；否则仅追加该链接，保留已有链接和所有执行事实。摘要冲突时重新读取并构造提案，最多重试三次；持续冲突或不明变化时保留现场，报告待补登记。

## 交付

按 [存储约定](storage.md) 整理必要的正式执行总结。最终回复直接提炼报告，给出 Run 与报告绝对路径、各结果数量、必要遗留与人工事项，不在生成前另写一份完整结束总结。0.12 报告未生成或未登记时分别说明执行状态与报告缺口，给出 `$cadra report`、`Run：<准确 run-id>`；已有未登记报告另附 `补充：补登记已生成报告：<准确绝对路径>`。

给出准确下一步：未完成先按执行归属区分活跃/已停止/未知，仅确认停止且可核对时建议 resume；结束后的失败恢复用显式 run，需求变更用 add/ready。

## 小组与资源视图

按 [小组调度](scheduling.md#视图与报告口径) 派生组、资源与验证信息；缺失时间不推算，角色会话数不等于同时执行阶段数，报告区分检查类型且不承诺固定加速。

## 收尾一致性结果

按 [收尾记录](closeout.md) 引用本 Run 的覆盖候选、收尾任务、findings 和整改／复审／验证证据，明确 passed、过期、未执行、blocked 或 failed。未执行／用户停止不声称通过；原业务任务失败不因收尾整改被重写。自动报告时仍只汇总冻结结果，不新增审查调用。

## 逐任务运行过程

```text
python3 -B <本次实际 Cadra 目录>/scripts/process_view.py --run <Run绝对路径>
```

[process_view.py](../scripts/process_view.py) 只读所选 0.12 Run，复用包内解析、校验与调度重放，stdout 为紧凑 JSON。它不读当前 Task／Cohestra 索引、不取代验收、不核实外部工具活性；新旧 0.12 Run 使用同一读取路径，无迁移或补写。运行中亦可显式 report；Run 读取变化须重读，不缓存上次视图。JSON 仅是报告输入，不是新的持久化协议或控制状态。

工具在投影前核对已保存交付契约的必填形状、类型、枚举及基础字段一致性；当前阶段为 validate 且 acceptance=passed 时，还须同时具有阶段／任务 completed、next=null/false/task_completed、blocked=false/null。声称保存了契约但字段损坏或上述完成字段冲突时明确失败，stdout 不输出正常视图。完全缺少交付时仍按 unknown 处理；可选 findings／acceptance 缺省或 null、未记录的 unresolved 仍保持未知，不补造零计数。此校验只核对记录内部约束，不重新裁决历史验收或外部证据。

- 每个任务（含收尾任务）都按 Run.tasks 顺序展示一条实际阶段路径；阶段按 calls 的 id，轮次取该调用已登记交付，不按 flow 补齐未执行阶段。未调用的任务写未调用及已登记原因；已有结果沿用收尾写来源，不冒称执行。previous_run 只作恢复来源，未经明确要求不拼成跨 Run 全量历史。
- `status=pending` 的调用显示“待派发”或“已派发、交付待核对”；`unknown` 与 gaps 如实展示。`recorded` 只表示 Run 保存了交付，真实性仍以引用证据为准。index_sync 未记录显示未知，明确失败不能展示为同步成功。缺少完成时间不以最终任务时间／下一调用时间补齐，不推算时长。
- 顺利任务用阶段路径和结果即可。有 findings、整改、验证失败／不确定、受阻或恢复的任务展开“阶段／轮次｜结果与问题｜处理及证据”表。依据工具给出的引用，按需读取对应不可变 handoff 整理问题 ID、现象、原因、修改和验证；只有计数时写“问题详情未知”，不能从计数下降推断某个 ID 已关闭。
- fix 的零 findings 是作者整改声明，review 的关闭结论才按其实际独立身份和候选来源标为独立复审确认。复审仍有问题时保留该轮结果；第二次整改和后续通过不能覆盖第一次失败。验证先失败后通过逐次保留，不把编译失败且零测试写成测试通过。
- 按 event_ids 对应的调度事件补充重要资源等待、验证 outcome（含 failed/inconclusive/interrupted）、候选失效与恢复。跨任务事件保持原 event id，不能凭缺失时间拼接总时间线；ownership_history 单列中断／接管事实，不因代次变化断言工具已停止。
- 按每次 finish 的 `timing.seconds` 展示授予回读到进程启动（grant_to_start）、外层命令进程耗时（command）、进程退出到登记回读（end_to_finish）、登记回读到原角色续接（finish_to_resume）。文件续接获授（finish_to_files_grant）与资源占用（grant_to_finish）单列。同一事件或续接的重复时间可合并，缺失、相互冲突或顺序矛盾的观察标未知。`timing.event_seconds` 仅表示日志事件间隔，可单列作历史对照。未 finish 的请求保留实际调度状态和中止事实。两段超过 10 秒时附 `delay_reasons` 的有据原因，未记录则写原因未知。只有已知分段参与汇总，注明已知次数。
- 对照优化效果时分别汇总业务整改与收尾整改轮数，并按原始证据核对同候选、同完整 argv、同必要输入及工具链的实际重复验证。证据不足时标未知。引用已有证据不计执行，条件变化后的重测单列原因。
- 原生证据缺口与已完成工程过程分开：例如“code → review（问题 A）→ fix → review（仍未关闭）→ fix → review（确认关闭）→ validate（缺设备证据 blocked）”，不得压缩为只有 blocked／零 findings。该示例不是所有任务的必经路线。
- 历史过程只使用该 Run 的冻结结果和当时引用交付。当前 README、后续 Run 或新修复不能填补旧结果；缺失信息标 unknown。报告仍按原轮次规则新增并登记，保留旧报告与原结果。

最终对话只提炼数量、关键整改和遗留，链接完整过程报告；不把所有任务明细、原始日志、完整角色身份或摘要值重复贴到对话。
